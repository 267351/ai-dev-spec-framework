## 设计方案：待批准目录（Pending Approval Directory）机制

### 背景问题

vibing-coding 模式下，AI 频繁生成需要用户审核的长内容（spec.md、架构方案、部署变更等）。内联展示导致：
1. **审核疲劳**：内容太长，用户被迫当场读完决策 → 虚假审批或拖延
2. **上下文污染**：长内容占据对话窗口 → AI 后续对话变慢变笨
3. **缺乏异步审核**：不能在自己节奏下审，不能查代码/问同事后再决策

### 机制描述

AI 将需要深度审核的内容写入 `pending/` 目录，文件状态为"待批准"。后续不阻塞执行。用户自行打开文件审核，签字确认后 AI 再执行。

```bash
pending/
├── APPROVED/          ← 签字后的文件
├── REJECTED/          ← 拒绝的提案
├── 2026-06-18-架构分层调整.md
├── 2026-06-18-新增MaterialType策略.md
└── REVIEW_REMINDER.md  ← 自动生成，待审清单
```

### 判断矩阵：什么适合 pending

| 不适合 | 适合 |
|--------|------|
| 简单确认（"继续下一步？"） | 架构决策（新增/修改约束） |
| 代码风格选择 | spec.md 创建/修改 |
| 即时应答型问题 | 部署方案变更 |
| 不影响后续操作的决策 | 需查代码/问同事的决策 |
| 短内容（<5 行） | 长内容（>50 行） |

### 好处

| # | 好处 | 详细 |
|---|------|------|
| 1 | 解决审核疲劳 | "审"和"写代码"解耦——审的时候专心审 |
| 2 | 适合深度决策 | 架构约束、可信度标注等需要查代码、想场景 |
| 3 | 防止上下文污染 | pending 文件不占对话窗口，AI 保持精简 |
| 4 | 天然审计追踪 | 创建/审核时间、批准/拒绝状态可追溯 |
| 5 | 支持异步协作 | A 编码时 AI 提建议，B（架构负责人）异步审核 |
| 6 | 减少虚假审批 | 没有"AI 在等你"的心理压力 |
| 7 | 与 spec-tools 衔接 | 已有 `spec_review_reminder.py` 支撑 |

### 坏处

| # | 坏处 | 缓解策略 |
|---|------|----------|
| 1 | 文件可能永不审核 | `REVIEW_REMINDER.md` 提醒 + 7天过期标记 |
| 2 | 审核时提案已过时 | 关联文件字段 + 过期后自动作废 |
| 3 | 失去对话上下文 | pending 文件自带"提出原因"摘要 |
| 4 | 文件爆炸（稀释信任） | 严格写入门槛：仅深度审核内容 |
| 5 | 精神状态切换成本 | 用户自己选择审核时间 |
| 6 | 区分门槛模糊 | 明确定义：>50行OR架构级→pending |
| 7 | 代码变更导致冲突 | AI 打开 pending 时重新检查关联文件是否变更 |
| 8 | Git 噪音 | APPROVED/REJECTED 不提交到 git |

### 待批准文件模板

```markdown
> [状态: 待批准]
> [提出者: AI (模型)]
> [提出时间: 2026-06-18 14:30]
> [关联文件: src/Core/Services/WorkloadService.cs]
> [类型: 架构约束 / spec.md / 部署方案 / 其他]

## 提案内容
（AI 生成的完整内容）

## 审批
- [ ] ✅ 批准（签字: ______  日期: ______）
- [ ] ❌ 拒绝（原因: ______）
- [ ] ⏸️ 暂缓（理由: ______）
```

### 关键约束

1. **只写需要深度审核的内容**，简单确认不走 pending
2. **写文件时必须附带"关联文件"**，方便用户跳转查看代码上下文
3. **AI 写 pending 后不等待**，继续执行不依赖该提案的任务
4. **超过 7 天未审自动标记过期**（`spec_review_reminder.py` 集成）
5. **每次 AI 会话开始提醒待审文件数**
6. **APPROVED/REJECTED 不提交 git**（除非用户明确要求）

### 结论

**可行，用处大，但必须严格限定范围。** 核心价值：把"需要深度思考的审核"从编码流程中剥离。最大风险不是技术实现，而是"文件写了没人看"——需用提醒工具 + 约定纪律对抗。
