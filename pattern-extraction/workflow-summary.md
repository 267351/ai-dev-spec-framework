# 可复用的AI辅助开发规范体系

## 📌 项目概述

### 项目名称
**可复用的AI辅助开发规范体系**

### 研究背景
当前AI辅助开发工具（如Copilot、Cursor等）在编码过程中存在"乱写代码"的问题，缺乏统一的规范约束。本项目旨在从实际项目中提炼出一套可复用的开发规范，使AI在协助开发时有章可循，确保代码质量和一致性。

### 目标与产出（线性关系）

| 阶段 | 目标 | 产出 | 依赖 |
|------|------|------|------|
| **第一阶段** | 按"可复用的AI辅助开发规范体系"对两个项目进行系统性总结 | 完整的规范体系文档 | 无 |
| **第二阶段** | 基于第一阶段的总结结果撰写学术论文 | 学术论文 | 第一阶段完成 |

**关键理解**：这是**线性关系**——先完成项目总结，再基于总结撰写论文。总结是论文的基础和前提。

## 🔥 核心工作原则（最高优先级）

### 原则一：启用头脑风暴
**每一次执行任务时，都要进行特别认真的思考和详细查询，往死里查，查到全部到位。**

- 任务开始前，必须进行全面的信息收集和调研
- 使用多维度搜索：代码库分析、文档查阅、外部资料检索
- 不满足于表面信息，深入挖掘底层逻辑和设计意图
- 记录所有发现，确保不遗漏任何关键细节

### 原则二：制定详细计划与技术方案
**每一次执行任务时，都要制定详细的计划跟技术方案，确保 AI 在断开后重新连接时，任务能接得上，且意图保持不变。**

- 任务开始前，必须输出书面的执行计划
- 计划包含：目标、步骤、依赖、验收标准、风险点
- 每个步骤必须有明确的输入/输出定义
- 计划存档于工作目录，确保可追溯、可恢复

## 🎯 核心目标

### 目标一：总结创作逻辑（方法论提炼）
从两个源项目中提取可复用的开发方法论：

| 提取维度 | 具体内容 |
|----------|----------|
| **架构模式** | MVC、微服务、单体等架构选型和应用 |
| **代码组织** | 模块划分、目录结构、文件命名规范 |
| **命名规范** | 变量、函数、类、接口的命名风格 |
| **错误处理** | 异常捕获、错误传播、日志记录策略 |
| **测试策略** | 单元测试、集成测试、测试覆盖率要求 |
| **依赖管理** | 包管理、版本控制、依赖锁定策略 |
| **配置管理** | 环境变量、配置文件、敏感信息处理 |

### 目标二：固化工作流程（Skills提炼）
将项目中的隐性知识显性化为可执行的Skills：

| 流程维度 | 固化内容 |
|----------|----------|
| **代码审查** | 审查流程、检查点、质量标准 |
| **Git规范** | 提交信息格式、分支策略、合并流程 |
| **部署流程** | 环境管理、部署步骤、回滚机制 |
| **文档规范** | 文档类型、维护频率、更新触发条件 |
| **质量门禁** | 自动化检查、人工审查、准入准出标准 |

### 目标三：引导任务执行（计划模板）
创建标准化的AI任务执行模板：

| 模板类型 | 包含要素 |
|----------|----------|
| **任务分解** | 子任务划分、依赖关系、优先级排序 |
| **验收标准** | 功能验收、性能验收、代码质量验收 |
| **质量检查点** | 代码审查点、测试执行点、文档更新点 |
| **风险识别** | 技术风险、进度风险、质量风险及应对策略 |

## 📜 工作规则

### 基本规则
1. **输出统一**：所有总结内容（文档、分析报告、论文草稿等）统一存放在 `tools` 文件夹下
2. **源文件保护**：源代码和原始文件保持在各自项目文件夹中，不做任何修改
3. **全面覆盖**：总结应涵盖代码结构、功能说明、关键模块、设计模式等核心内容

### 分析原则
4. **分层提取**：先提取两个项目的共同模式，再识别各自的特殊实践
5. **可验证性**：每个提炼的Skill都应该有明确的检查标准，AI可以自我验证
6. **渐进式**：先从核心规范开始，再逐步扩展到细节规范
7. **实战导向**：提炼的规范应该能直接指导AI写代码，而非仅供人类阅读

## ⚠️ 关键注意事项

### 技术层面
| 维度 | 注意事项 |
|------|----------|
| **抽象层次** | 平衡具体实现和通用原则，太具体难以复用，太抽象缺乏指导性 |
| **项目差异性** | 两个项目可能有不同风格，需要识别共同点和差异点 |
| **版本演进** | 规范需要随技术发展更新，避免僵化 |
| **AI适配性** | 提炼的skills需要是AI可执行的、可验证的，而非模糊的原则 |
| **优先级排序** | 区分红线规范（必须遵守）和最佳实践（建议遵守） |

### 流程层面
| 维度 | 注意事项 |
|------|----------|
| **敏感信息** | 代码中是否有配置、密钥等不应出现在总结中的内容 |
| **版权问题** | 确保提取的规范不侵犯原项目的知识产权 |
| **可验证性** | 每个规范都应该有明确的检查标准和验证方法 |
| **渐进式** | 先从核心规范开始，再逐步扩展到细节规范 |
