# 第3章 方法论：规范体系设计

## 3.1 设计原则

### 3.1.1 可验证性原则

规范必须有明确的检查标准，能够被自动化工具或人工审查验证。这一原则确保规范不是模糊的指导原则，而是可执行的具体要求。

**实现方式**：
- 为每个规范定义明确的验证标准
- 提供自动化检查命令
- 区分红线规范（必须遵守）和最佳实践（建议遵守）

**示例**：
```markdown
## C01：分层架构

### 验证标准
1. 依赖方向正确 - 检查ProjectReference方向
2. 无反向引用 - 下层项目不引用上层项目
3. 接口解耦 - 通过接口而非具体类依赖

### 验证命令
```bash
# 检查依赖方向
dotnet build 2>&1 | grep "circular dependency"

# 检查ProjectReference
grep -r "ProjectReference" src/ --include="*.csproj"
```
```

### 3.1.2 可复用性原则

规范可以应用于不同项目，不受特定技术栈或业务领域的限制。这一原则确保规范体系具有广泛的适用性。

**实现方式**：
- 提取通用的开发模式，而非特定项目的实现细节
- 分离通用规范和特定场景规范
- 提供规范组合建议，支持不同类型的项目

**示例**：
```markdown
## 通用规范（适用于所有项目）
- 分层架构规范
- 命名约定规范
- Conventional Commits规范
- Spec.md约定文件体系
- 结构化日志规范
- 单元测试规范

## 特定场景规范（根据项目需求选择）
- 实时通信规范（SignalR/Blazor Server）
- 错误处理规范（异常/Result模式）
- 硬件抽象规范（HAL层）
- 部署自动化规范（脚本/CI/CD）
- 策略模式规范（可扩展业务逻辑）
```

### 3.1.3 AI适配性原则

规范可以被AI理解和执行，能够有效指导AI的代码生成行为。这一原则确保规范体系能够真正解决AI辅助开发中的"乱写代码"问题。

**实现方式**：
- 使用结构化的规范格式，便于AI解析
- 提供明确的验证标准，便于AI自我检查
- 设计按需加载机制，适应AI的上下文窗口限制

**示例**：
```markdown
## AI辅助开发专用规范

### AGENTS.md知识索引架构
- 精简索引（≤100行）
- 按需加载机制
- 知识分层体系

### Spec.md约定文件体系
- 核心文件有对应.spec.md
- 修改前必须审查spec.md
- 新坑点记录到spec.md
```

## 3.2 体系架构

### 3.2.1 三层架构设计

规范体系采用三层架构设计，从核心到场景逐层扩展：

```
┌─────────────────────────────────────────────────────────────┐
│                    L1: 核心规范层                            │
│              （必须遵守，红线规范）                           │
├─────────────────────────────────────────────────────────────┤
│                    L2: 最佳实践层                            │
│              （建议遵守，推荐规范）                           │
├─────────────────────────────────────────────────────────────┤
│                    L3: 场景规范层                            │
│              （按需选择，特定场景）                           │
└─────────────────────────────────────────────────────────────┘
```

**L1: 核心规范层**：
- 定义必须遵守的红线规范
- 包括架构铁律、命名约定、安全规范
- 验证方式：自动化检查+人工审查

**L2: 最佳实践层**：
- 定义建议遵守的推荐规范
- 包括设计模式、编码风格、测试规范
- 验证方式：代码审查+工具检查

**L3: 场景规范层**：
- 定义特定场景的规范
- 包括硬件抽象、实时通信、部署规范
- 验证方式：场景匹配+专家评审

### 3.2.2 六大领域分类

规范按领域分为六大类：

| 领域 | L1核心规范 | L2最佳实践 | L3场景规范 |
|------|------------|------------|------------|
| **架构** | 分层架构、依赖方向 | Repository模式、Unit of Work | HAL层、双子系统、微服务 |
| **编码** | 命名约定、异步编程 | 结构化日志、错误处理 | Result模式、API异常处理 |
| **流程** | Spec.md体系、Conventional Commits | 代码审查、文档管理 | AGENTS.md索引、偏差检测 |
| **测试** | 单元测试 | 测试覆盖、测试基类 | SQLite内存测试、集成测试 |
| **部署** | 版本管理 | 部署脚本、回滚机制 | 一键跨平台、Kiosk模式 |
| **文档** | XML文档注释 | 架构文档、变更日志 | 业务规则引用、坑点记录 |

### 3.2.3 规范关系设计

规范之间存在依赖和组合关系：

**依赖关系**：
```
C01 分层架构
├── B01 Repository模式
├── B02 Unit of Work
├── S01 硬件抽象层
├── S02 双子系统架构
└── S03 三大系统边界

C02 命名约定
├── B03 结构化日志
└── B04 错误处理

C04 Spec.md体系
├── S08 AGENTS.md索引
├── S09 偏差检测
└── S15 坑点记录

C06 单元测试
├── B06 测试覆盖
└── S10 SQLite内存测试
```

**组合关系**：
| 组合名称 | 包含规范 | 适用场景 |
|----------|----------|----------|
| **Web API规范** | C01 + C02 + C03 + B03 + B04 + S06 | RESTful API开发 |
| **Blazor规范** | C01 + C02 + C03 + C04 + B01 + B02 | Blazor应用开发 |
| **工业应用规范** | C01 + C02 + C04 + S01 + S11 + S12 + S13 | 物联网/工业应用 |
| **AI辅助开发规范** | C04 + C05 + S08 + S09 + S15 | AI辅助开发 |
| **企业应用规范** | C01 + C02 + C03 + C06 + B01 + B02 + S05 | 企业级应用 |

## 3.3 提取方法

### 3.3.1 代码模式识别

通过分析源代码，识别项目中使用的编码模式和最佳实践。

**分析维度**：
- 命名规范：变量、函数、类、接口的命名风格
- 代码风格：缩进、空格、换行、注释风格
- 错误处理：异常捕获、错误传播、错误日志
- 日志规范：日志级别、日志格式、日志位置

**分析方法**：
1. 使用静态分析工具扫描代码
2. 人工审查关键模块
3. 提取共同模式

**示例**：
```markdown
## 命名规范提取结果

| 元素 | 约定 | 示例 |
|------|------|------|
| Namespace | PascalCase | `LimitedSpaceForeignObject.BLL.Services` |
| Class | PascalCase | `GoodsService` |
| Interface | I前缀+PascalCase | `IGoodsService` |
| Method | PascalCase | `GetByIdAsync` |
| Property | PascalCase | `GoodsName` |
| Private Field | _camelCase | `_goodsRepository` |
| Parameter | camelCase | `goodsCode` |
| Local Variable | camelCase | `existingSession` |
| Async Method | Async后缀 | `GetByIdAsync` |
```

### 3.3.2 提交历史分析

通过分析Git提交历史，识别项目的工作流程和变更管理规范。

**分析维度**：
- 提交信息格式：Conventional Commits等
- 分支策略：main/develop/feature等
- 合并策略：merge/rebase/squash等
- 变更频率：每日提交、功能完成提交等

**分析方法**：
1. 使用git log分析提交历史
2. 提取提交信息模式
3. 分析分支和合并策略

**示例**：
```markdown
## 提交信息格式提取结果

**格式**：`type(scope): description`

**类型分布**：
| 类型 | 数量 | 百分比 |
|------|------|--------|
| `feat` | 56 | 42% |
| `fix` | 42 | 32% |
| `docs` | 15 | 11% |
| `refactor` | 10 | 8% |
| `chore` | 6 | 5% |
| `test` | 3 | 2% |
```

### 3.3.3 文档规范提取

通过分析项目文档，识别文档规范和知识管理方式。

**分析维度**：
- 文档类型：README、CHANGELOG、API文档等
- 文档结构：章节组织、格式规范
- 知识管理：坑点记录、业务规则引用等
- 维护机制：更新频率、更新触发条件

**分析方法**：
1. 扫描docs/目录
2. 分析文档内容和结构
3. 提取文档规范

**示例**：
```markdown
## 文档规范提取结果

### Spec.md约定文件体系
- 核心文件有对应.spec.md
- 记录：文件用途、踩过的坑、禁止修改的内容
- 修改代码前必须检查spec.md
- 修改后主动询问是否更新spec.md

### 业务规则引用
- 格式：BR-xxx-xxx
- 示例：BR-USER-02（工号、卡号唯一）
- 记录在docs/业务规则参考.md
```

### 3.3.4 架构模式识别

通过分析项目架构，识别使用的架构模式和设计模式。

**分析维度**：
- 分层结构：表现层/业务层/数据层的划分
- 模块划分：模块边界、职责划分
- 依赖关系：模块间依赖、外部依赖
- 通信机制：API设计、消息队列、事件驱动

**分析方法**：
1. 分析解决方案结构
2. 检查项目依赖关系
3. 识别架构模式

**示例**：
```markdown
## 架构模式提取结果

### 分层架构
- Models <- DAL <- BLL <- Api <- App
- 依赖方向单向（上层依赖下层）
- 禁止反向引用（下层不能引用上层）

### Repository模式
- 接口+实现分离
- 封装CRUD操作
- 不包含业务逻辑
- 通过DI注册
```

## 3.4 验证机制

### 3.4.1 验证层次设计

规范验证分为四个层次：

| 层次 | 验证方式 | 工具 | 频率 |
|------|----------|------|------|
| **自动化检查** | 静态分析、编译检查 | Roslyn Analyzer, dotnet build | 每次提交 |
| **工具检查** | 代码风格、命名约定 | EditorConfig, StyleCop | 每次提交 |
| **代码审查** | 逻辑正确性、规范遵循 | PR审查 | 每次合并 |
| **专家评审** | 架构设计、场景适用性 | 人工评审 | 重大变更 |

### 3.4.2 验证标准格式

为每个规范定义标准的验证格式：

```markdown
## 规范名称

### 验证标准
1. [检查项1] - [验证方法]
2. [检查项2] - [验证方法]
3. [检查项3] - [验证方法]

### 验证命令
```bash
# 自动化检查
dotnet build
dotnet test

# 工具检查
dotnet format --verify-no-changes
```

### 验证结果
- ✅ 通过：所有检查项都满足
- ❌ 失败：有检查项不满足，需要修复
```

### 3.4.3 红线规范与最佳实践

区分红线规范（必须遵守）和最佳实践（建议遵守）：

**红线规范**：
- 违反红线规范的代码不能合并到主分支
- 验证方式：自动化检查+人工审查
- 处理方式：必须修复才能通过

**最佳实践**：
- 建议遵守但不强制的规范
- 验证方式：代码审查+工具检查
- 处理方式：可以有例外，但需要说明原因
