# 第3章 案例研究设计

本章描述本研究采用的研究方法。本研究采用**多案例嵌入式案例研究**（multiple-case embedded case study）方法，以两个工业项目（CSO-FORCS 和 WarehouseMS）为研究案例，对它们的 spec.md 规范体系进行深度分析。案例研究适用于"如何"（how）和"为什么"（why）类型的研究问题（Yin, 2018），与本研究的研究问题高度匹配。

## 3.1 案例选择

### 3.1.1 选择策略

案例选择遵循"最大相似系统中的最大差异"（most-different in most-similar systems）策略。具体而言：

- **相似性控制**：两个项目使用相同的技术栈（C# + Blazor + EF Core/SQL Server）、相同的 AI 编码工具（OpenCode）、相同的规范体系框架（AGENTS.md + spec.md）、并由同一团队开发。这些因素被控制为常量。
- **差异性关注**：两个项目在 AGENTS.md 的设计决策上产生了显著分歧（精简索引风格 vs 完整手册风格），在 spec.md 的命名规范和维护模式上也走向了不同的演化路径。这些差异构成了对比分析的核心变量。

选择这一策略的理由是：当技术栈、工具链、团队背景等变量被控制后，AGENTS.md 的设计决策对 spec.md 体系健康度的独立影响能够被更清晰地观察。

### 3.1.2 CSO-FORCS 项目概览

CSO-FORCS 是一个面向特定行业的操作管理系统，采用 C# / ASP.NET Core Blazor / Entity Framework Core 技术栈。项目整体结构如下：

- **解决方案结构**：包含 12 个子项目，采用五层架构（Models → DAL → BLL → API → Blazor App）
- **代码规模**：中等规模，包含约 200+ 源文件
- **AGENTS.md 设计**：精简索引风格，82 行，侧重于提供导航而非完整内容，依赖 OpenCode 的 Skill 机制按需加载规范
- **spec.md 体系**：严格遵循命名规范，架构总纲.spec.md（242 行）作为项目级约束，30+ 文件级 spec.md 覆盖核心模块
- **创新特征**：引入了偏差检测机制（硬偏差/软偏差/演进偏差三级分类）和 AGENTS.md.spec.md（531 行元规范），对 spec.md 体系本身的设计进行了规范化

### 3.1.3 WarehouseMS 项目概览

WarehouseMS 是一个通用仓储管理系统，采用与 CSO-FORCS 相同的 C# / ASP.NET Core Blazor / SQL Server 技术栈。项目整体结构如下：

- **解决方案结构**：包含 3 个子项目（Client / Server / Shared），采用简化的三层架构
- **代码规模**：较小规模，包含约 40+ 源文件
- **AGENTS.md 设计**：完整手册风格，303 行，自包含大量的 Skill 定义和操作流程，违反了"精简索引"的 ≤100 行原则
- **spec.md 体系**：采用两种不同的 spec.md 命名规范（`*.spec.md` 和 `.spec.md`），约 20+ 文件级 spec.md，存在较高的内容空壳率
- **对比价值**：与 CSO-FORCS 使用同一套规范体系框架但产出截然不同的演化结果，是理想的"对照案例"

### 3.1.4 可比性分析

表 3.1 总结了两个案例的可比性：

| 维度 | CSO-FORCS | WarehouseMS | 可比性 |
|------|-----------|-------------|--------|
| 技术栈 | C# / Blazor / EF Core | C# / Blazor / SQL Server | 高度可比 |
| AI 编码工具 | OpenCode | OpenCode | 完全相同 |
| 规范体系框架 | AGENTS.md + spec.md | AGENTS.md + spec.md | 完全相同 |
| AGENTS.md 行数 | 82 行 | 303 行 | 显著差异 ✓ |
| AGENTS.md 设计风格 | 精简索引 | 完整手册 | 显著差异 ✓ |
| 项目规模 | 中等（200+ 文件） | 较小（40+ 文件） | 中等差异 |
| spec.md 文件数 | 30+ | 20+ | 可比 |
| spec.md 命名规范 | 统一 | 两种模式混合 | 显著差异 ✓ |

两个项目在"应该怎样"（规范体系框架相同）上一致，在"实际上怎样"（设计决策和演化结果不同）上产生分歧——这正是案例研究方法所追求的"揭示因果机制"的理想条件。

## 3.2 数据收集方法

本研究收集了以下五类数据，每类数据服务于不同的分析目标。

### 3.2.1 spec.md 文件全量统计

**目标**：获取 spec.md 体系在两个项目中的宏观状态。

**收集内容**：
- 每个 spec.md 文件的路径、大小（字节）、行数、创建日期、最后修改日期
- .spec.md 后缀文件与对应代码文件的配对关系
- 架构总纲.spec.md 和目录级 spec.md 的内容行数与引用的下级文件数量

**收集方法**：使用 `find` 命令和 `spec_md_manager.py` 工具的输出日志进行全量扫描，生成 CSV 格式的统计数据集。

### 3.2.2 AGENTS.md 文本分析

**目标**：分析两个项目 AGENTS.md 的设计差异及其对规范体系的影响。

**收集内容**：
- AGENTS.md 的总行数、章节数、Skill 引用数量
- 每个章节的内容类型分类（纯导航 vs 内联定义 vs 混合）
- AGENTS.md 对 spec.md 文件的引用方式（直接路径引用 vs 间接索引引用）

**收集方法**：人工标注 AGENTS.md 的章节类型，结合 grep 统计引用密度。分析焦点为：AGENTS.md 是作为"导航地图"还是"完整手册"发挥作用。

### 3.2.3 关键文件的深度内容分析

**目标**：理解 spec.md 体系的核心设计模式和质量水平。

**分析对象**：
- CSO-FORCS 的 `架构总纲.spec.md`（242 行项目级约束）
- CSO-FORCS 的 `AGENTS.md.spec.md`（531 行元规范）
- WarehouseMS 的对应文件（如存在）
- 两个项目中代表性的文件级 spec.md（各选 5 个进行深度比较）

**分析维度**：
- 六章节模板的遵循度（结构完整性检查）
- 约束的具体性（"指名道姓"vs"抽象原则"的比例）
- "踩过的坑"章节的内容质量（是否有实质性内容 vs 占位符）
- 禁止性约束 vs 建议性约束的比例

### 3.2.4 自动化工具使用日志分析

**目标**：了解 spec_md_manager.py 工具在两个项目中的实际使用模式。

**收集内容**：
- 工具的调用频率和调用时间分布
- 工具的检查结果（"发现未配对 spec.md"的告警频率）
- 工具的创建模式（批量创建 vs 按需创建）

**收集方法**：分析工具的输出日志和项目中的工具配置文件。

### 3.2.5 LLM 模型使用记录

**目标**：了解不同能力层级的 LLM 模型在两个项目开发中的分工模式。

**收集内容**：
- 使用的模型类型及各自的任务范围
- 不同模型在 spec.md 编写、遵循、审查中的角色差异
- 模型切换的频率和触发条件

**收集方法**：基于开发团队的实践记录和会话日志进行回顾性分析。

## 3.3 分析框架

### 3.3.1 四维度分析模型

本研究构建了"**创立 → 更新 → 效应 → 弊端**"的四维度分析模型，用于系统地解剖 spec.md 体系：

- **创立维度**：分析 spec.md 体系的创立动机（为什么需要它）、设计哲学（六个章节模板的设计意图）、以及层级化结构（架构总纲→目录级→文件级的三级约束传播）。
- **更新维度**：分析 spec.md 的标准更新链路（读取→修改→询问→审批）、CSO-FORCS 的创新（偏差检测与更新提醒机制）、以及更新机制在实践中遇到的摩擦。
- **效应维度**：分别分析正面效应（AI 跨会话知识延续、架构红线的分布式传播、隐性知识的显性化、上下文窗口的分层优化）和负面效应（七个系统性弊端）。
- **弊端维度**：分析弊端之间的因果关系，以及从七个弊端中提炼出的两个根本性缺陷。

这个四维度模型的优势在于：它不仅描述了 spec.md 体系"是什么"（创立维度）和"怎么变"（更新维度），还评估了它"产生了什么效果"（效应维度）和"哪里出了问题"（弊端维度），从而提供了一个完整的生命周期视角。

### 3.3.2 跨项目对比维度

跨项目对比在以下四个维度上展开：

1. **AGENTS.md 设计**：82 行的精简索引 vs 303 行的完整手册——两种设计对 spec.md 加载效率、认知负载、AI 遵循度的影响。
2. **spec.md 命名规范**：统一的 `*.spec.md` vs 混合的 `*.spec.md` + `.spec.md`——命名不一致如何影响自动化工具的准确性和开发者的文件定位效率。
3. **模板遵循度**：六章节模板在两个项目中的实际填充率比较——哪些章节最容易被"空洞化"。
4. **内容健康度**：spec.md 中实质性约束 vs 占位符内容的比例、更新延迟（最后修改日期与代码修改日期的差距）。

### 3.3.3 失败模式识别框架

本研究借鉴了 CSO-FORCS 自身设计的**偏差检测三级分类**作为失败模式识别的基础框架：

- **硬偏差（Hard Deviation）**：完全违反 spec.md 中明确禁止的约定。例如 AI 违反了"禁止 Web 层直接引用 Infrastructure 层"的架构红线。
- **软偏差（Soft Deviation）**：部分符合但不够好的实践。例如 AI 提供了基本实现但缺少 spec.md 中要求的错误处理和日志记录。
- **演进偏差（Evolutionary Deviation）**：spec.md 内容与代码演进方向不一致。例如 spec.md 记录了旧的架构约束，但代码已经演进到新架构。

在此框架基础上，本研究进一步识别了**系统层面**（而非单文件层面）的失败模式——即体系整体的设计缺陷导致的不只是个别违规，而是系统性的质量退化。

### 3.3.4 根因分析方法

对于识别出的失败模式，采用"**五问法**"（Five Whys）进行根因追溯：

- 症状层：AI 违反了一条 spec.md 约束。
- 直接原因：AI 在生成长代码时"忘记"了约束。
- 系统原因：约束没有被重复注入到 AI 的上下文中。
- 设计原因：规范体系缺乏自动验证机制，无法在 AI 输出后立即检查。
- 根因：自动验证闭环的缺失——规范写入后，完全依赖 AI 的"自觉"。

这种从症状到设计根因的追溯方法确保了分析的深度，避免了停留在表面现象。

## 3.4 研究有效性的威胁

### 3.4.1 外部有效性（External Validity）

**威胁**：研究结果的推广性。本研究仅基于两个特定项目，且均为 C# / Blazor 技术栈，由同一团队开发。

**缓解措施**：
- 详细描述了案例的上下文特征，使读者能够判断研究结果是否适用于其自身场景。
- 在分析中区分了"技术栈特定的发现"和"技术栈无关的发现"（如 AGENTS.md 的设计原则是通用的，而 spec_md_manager.py 的工具链异质性问题与 Python/C# 混合场景特定相关）。
- 第 7 章明确讨论了推广到其他技术栈（如 Java/Spring、Python/Django）时需要注意的差异。

### 3.4.2 内部有效性（Internal Validity）

**威胁**：因果推断的可靠性。AGENTS.md 设计差异与 spec.md 体系健康度之间的因果关系可能受到混淆变量的影响（如项目规模差异、开发阶段差异）。

**缓解措施**：
- 在对比分析中显式考虑了项目规模等混淆变量的影响，并对分析结论进行了限定。
- 使用了"过程追踪"（process tracing）方法——不是简单地比较最终状态，而是追溯两个项目的 spec.md 体系从建立到当前的演化过程，以建立因果链。

### 3.4.3 构念有效性（Construct Validity）

**威胁**：测量指标是否真实反映所研究的构念。例如，"spec.md 内容空壳率"作为"规范体系健康度"的测量指标是否有效。

**缓解措施**：
- 使用多指标三角验证（triangulation）：不依赖单一指标，而是综合使用行数、更新延迟、模板填充率、实质性约束比例等多个指标。
- 提供了每个指标的操作定义，使研究的可复现性得到保障。

### 3.4.4 可靠性（Reliability）

**威胁**：研究过程的可复现性。深度内容分析中的人工判断（如"约束的具体性"分类）可能受研究者主观影响。

**缓解措施**：
- 对关键分类（如约束的具体性）提供了明确的分类标准和示例。
- 所有数据（spec.md 统计、AGENTS.md 文本）均来自项目文件的客观记录，不依赖主观回忆。
- 研究数据（spec.md 文件内容、统计结果）可在源项目中直接验证。
