## 摘要

AI 辅助开发规范体系（如 spec.md）的现有研究隐含了一个未经检验的假设：规范体系的效果取决于规范本身的设计质量，与执行规范的具体 LLM 模型无关。本研究通过对两个工业项目中三种不同能力层级 LLM 模型（Claude Opus 4.8、DeepSeek 4.0、小米 MIMO 2.5 PRO）的实际使用观察，揭示了这一假设的谬误。实证数据显示：同一套 spec.md 体系，在架构级模型上可有效转化为架构约束，在实现级模型上需要操作性表述才能正确执行，在辅助级模型上几乎完全无效——约束必须内联在 Prompt 中。基于此发现，本研究提出了模型感知的规范设计策略，核心原则为"规范密度与模型能力反向匹配"：模型越弱，规范越要细、越少、越具体。进一步提出了分层约束表述方法（同一条规则对三个模型层级采用原则性/操作性/模板式三种表述）、混合流水线架构（强模型决策→中模型实现→弱模型原子任务→强模型审查）、以及元 Skills 框架（关于如何管理规范体系本身的 6 个元技能）。初步在 CSO-FORCS 项目上的混合流水线实践表明，该方案可在不显著降低代码质量的前提下降低约 40% 的模型调用成本。

**关键词**: AI 辅助开发；LLM 模型能力；规范体系；模型感知设计；混合流水线；元 Skills

# 第1章 引言：被忽视的变量——LLM 模型能力

## 1.1 研究背景

### 1.1.1 从"建立规范"到"规范失效"再到"为什么失效"

本研究的前两个版本建立了递进的认识：

**v1（成功报告型）** 回答了"如何建立 AI 辅助开发规范体系"——从两个工业项目中提取了 45 个规范并构建了三层架构。

**v2（问题驱动型）** 揭示了"规范体系建立后会产生什么问题"——识别了七个系统性弊端和两个根本性缺陷（验证闭环缺失 + 错误约定毒性），提出了六项改进方案。

但 v2 遗留了一个未充分展开的观察：**同一套规范体系，在不同模型上的表现截然不同**。v2 第 6.8 节仅用 300 字提及了模型感知策略，第 4.4.6 节分析了 AGENTS.md 设计分歧（82 行 vs 303 行），但未深入探究一个更深层的问题：

> 规范体系的"好"是绝对的还是相对于模型的？为 Claude Opus 4.8 设计的规范体系，对 DeepSeek 4.0 或小米 MIMO 2.5 PRO 是否同样有效？

### 1.1.2 一个被忽视的变量

在 AI 辅助开发规范的讨论中，隐含着一个未经检验的假设：**规范体系的效果取决于规范本身的设计质量，与执行规范的具体模型无关**。这个假设导致研究和实践都聚焦于"规范应该怎么写"，而非"写给谁"。

但在两个项目的实际开发中，我们使用了三种不同能力层级的 LLM 模型：

| 模型 | 能力层级 | 主要任务 |
|------|----------|----------|
| Claude Opus 4.8 | 架构级 | 架构设计、核心决策、代码审查、spec.md 编写 |
| DeepSeek 4.0 | 实现级 | 日常开发、Service/Repository 实现、功能迭代 |
| 小米 MIMO 2.5 PRO | 辅助级 | Entity/DTO 定义、简单 CRUD、模板化页面 |

实践中的观察是：同一套 spec.md 体系，Claude Opus 4.8 能够理解抽象约束并转化为正确的设计决策，DeepSeek 4.0 能够遵循具体约束但在长会话中衰减，小米 MIMO 2.5 PRO 几乎无法从外部 spec.md 中受益——约束必须内联在 Prompt 中才有效。

这一观察指向一个关键洞察：**LLM 模型能力是规范体系效果的一个独立变量，其影响力可能不低于规范本身的设计质量**。

## 1.2 问题定义

本研究聚焦的核心问题是：

> **LLM 模型的能力差异如何影响 AI 辅助开发规范体系（spec.md）的实际效果？如何设计模型感知的规范体系，使不同能力的模型都能被有效约束？**

具体而言，回答以下研究问题：

- **RQ1（能力分层）**：在规范遵循任务上，不同能力层级的 LLM 模型表现出怎样的差异化行为？这些行为差异的边界在哪里？
- **RQ2（设计策略）**：针对不同能力层级的模型，规范体系应该采用怎样不同的设计策略（约束粒度、表达方式、加载策略、验证强度）？
- **RQ3（混合流水线）**：如何设计和验证一个多模型混合流水线，使不同能力的模型协同工作，同时确保规范约束在不同模型之间一致传播？

## 1.3 研究贡献

1. **首次系统性地分析了 LLM 模型能力对规范体系效果的差异化影响**。与已有研究关注"如何写好规范"不同，本研究关注"规范写给谁"这一前置条件。

2. **提出了规范密度与模型能力反向匹配原则**：模型越弱，规范要越细、越少、越具体；模型越强，规范可以越粗、越多、越抽象。这一定量原则为规范设计提供了模型感知的指导。

3. **设计了分层约束强度表**：同一条架构约束，对三种能力层级的模型分别采用原则性、操作性和代码模板式三种表述，确保约束在不同模型上的有效传递。

4. **提出了混合流水线的设计模式**：强模型负责架构设计、spec.md 编写和代码审查，中模型负责规范约束下的实现，弱模型负责原子任务——三个层级形成质量闭环。

5. **提出了元 Skills 框架**：在 Skills 体系之上定义了一套关于"如何管理 Skills 体系"的元技能，包括 Skills 提取方法论、价值评估、过期检测和矛盾检测。

6. **在 spec-tools 工具链中实现了模型感知的初步支持**：`spec_deploy_init.py` 的自动推理、约束表达的分层设计、以及 CI 验证的模型适配策略。

## 1.4 研究方法

本研究采用**参与式观察 + 案例对比分析**的方法。研究者参与了两个项目（CSO-FORCS 和 WarehouseMS）的完整开发过程，在实际开发中交替使用三种不同能力的 LLM 模型，记录了模型在规范遵循上的行为差异。

观察周期覆盖约 3 个月的实际开发活动，包括架构设计、功能实现、Bug 修复、代码重构等多种任务类型。数据来源包括：AI 会话日志中的代码输出、人工审查发现的违规记录、spec.md 的更新历史、以及工具的扫描报告。

- **第1章 引言**：研究背景、问题定义、研究贡献
- **第2章 相关工作**：LLM 能力评估、自适应系统、模型路由

# 第2章 相关工作

本章从三个维度综述与模型感知规范体系相关的工作：（1）LLM 模型的能力评估与分层；（2）AI 编码中的自适应策略与模型路由；（3）知识管理系统的自适应呈现。在此基础上指出研究空白。

## 2.1 LLM 模型能力评估与分层

### 2.1.1 模型能力基准测试

LLM 能力的评估已有丰富的基准测试体系。通用基准如 MMLU（Hendrycks et al., 2021）覆盖 57 个学科的知识测试，HumanEval（Chen et al., 2021）评估代码生成能力，BIG-bench（Srivastava et al., 2022）提供 200+ 个任务的多维度测试。代码特定基准如 SWE-bench（Jimenez et al., 2024）评估真实 GitHub Issue 的解决能力，DS-1000（Lai et al., 2023）评估数据科学代码生成。

这些基准测试的局限在于：它们测量的是模型在**独立任务**上的能力，而非模型在**持续约束下**的行为。例如，一个模型可能在 HumanEval 上达到 80% 的通过率，但这不保证它在 5 轮对话后仍然遵循"禁止 Web 层直接访问数据库"的约束。规范体系的有效性恰恰依赖于后一种能力——**持续约束遵循**，而非单次任务完成。

### 2.1.2 模型能力分层的研究

已有研究者提出了 LLM 能力的分层框架。Wei et al.（2022）识别了 LLM 的"涌现能力"（emergent abilities），发现某些能力仅在模型规模超过特定阈值后才会出现。这一发现暗示：如果规范遵循是一种涌现能力，那么弱模型可能**根本**不具备从外部规范文件中提取约束并内化的能力。

Kaplan et al.（2020）的缩放定律（scaling laws）为模型能力与计算量之间的关系提供了理论框架，但未涉及能力分层在工程实践中的应用意义。

在工业实践中，Zheng et al.（2023）的 LMSYS Chatbot Arena 通过人类偏好投票建立了模型能力的相对排名。但这类排名基于通用对话质量，未必能反映模型在"遵循项目特定架构约束"上的能力差异。

### 2.1.3 本研究的独特视角

已有研究建立了模型能力的测量和排名，但缺少一个关键连接：**将模型能力分层映射到规范体系的设计策略上**。换句话说，不是简单地知道"Claude Opus 4.8 比 DeepSeek 4.0 强"，而是知道"对于 Claude Opus 4.8，规范可以写成抽象原则；对于 DeepSeek 4.0，同一规范必须写成具体操作指令"。

## 2.2 AI 编码中的自适应与路由

### 2.2.1 模型路由（Model Routing）

模型路由是指根据任务特征选择最合适的模型来处理。Chen et al.（2024）提出了基于任务难度估计的自动路由策略，将简单任务导向小模型以降低成本，将复杂任务导向大模型以保证质量。OpenAI 的 GPT-4 与 GPT-3.5 的混合使用策略、以及 Anthropic 的 Haiku/Sonnet/Opus 三级分层都是模型路由的工业实践。

但这些路由策略基于**任务本身的难度**进行判断，而非基于**规范约束的复杂度**。在 AI 辅助开发的场景中，同一个"实现 Service 方法"的任务，如果关联的 spec.md 包含抽象架构约束，则需要强模型；如果 spec.md 仅包含命名约定，中模型即可胜任。现有路由策略无法捕捉这一维度的差异。

### 2.2.2 提示工程中的自适应策略

Few-shot prompting（Brown et al., 2020）、chain-of-thought（Wei et al., 2022）、以及 structured prompting（Yao et al., 2024 的 Tree of Thoughts）等技术都是通过调整提示格式来适配模型能力。这些技术的共同思路是：**用更多的提示结构来补偿模型能力的不足**。

本研究提出的"约束分层表述"策略与这一思路一致：对弱模型，使用代码模板式约束（相当于给模型提供了"约束的正例"）；对强模型，使用原则性约束（相当于让模型自行推导具体实现）。

### 2.2.3 IDE 工具中的模型适配

主流 AI 编码工具在模型适配方面仍处于初级阶段。GitHub Copilot 在不同模型间切换时使用相同的上下文构建策略，不会根据模型能力调整规范文件的加载量。Cursor 的 `.cursorrules` 对所有模型一视同仁。OpenCode 的 AGENTS.md / Skill 机制允许开发者手动控制加载策略，但缺乏自动化的模型感知适配。

## 2.3 自适应知识呈现

### 2.3.1 信息检索中的查询扩展

在信息检索领域，查询扩展（query expansion）技术根据用户查询的复杂度调整检索策略。简单查询使用精确匹配，复杂查询使用语义扩展（Carpineto & Romano, 2012）。这一思路与模型感知的规范加载策略高度类似：强模型能够理解"禁止跨层调用"的语义并进行扩展，弱模型需要"不要在 .razor.cs 中写 _dbContext"这样的精确约束。

### 2.3.2 自适应学习系统中的内容呈现

教育技术领域的自适应学习系统根据学习者的能力水平调整教学内容的呈现方式（Brusilovsky, 2001）。初学者收到步骤化的操作指导，高级学习者收到原则性的概念解释。这种"内容适应学习者"的模式与本研究提出的"规范适应模型"模式在逻辑上完全一致——将 LLM 模型视为规范体系的"学习者"。

## 2.4 研究空白

基于上述综述，识别以下空白：

1. **模型能力分层 → 规范设计策略的映射研究缺失**。已有研究分别讨论了模型能力评估和规范体系设计，但两者之间的桥梁——"如何根据模型能力设计规范"——几乎未被探索。

2. **多模型混合流水线中的规范一致性传播**。已有模型路由研究关注任务的"分派"，未关注规范约束在模型间的"传递"。当强模型设计的架构约束需要被中模型在执行时遵循，如何确保约束在传递过程中不降级、不丢失、不误解？

3. **规范遵循能力的纵向衰减规律**。模型在长会话中的约束遵循衰减（DeepSeek 4.0 前 3 轮严格，第 5 轮出现违规）在已有文献中几乎未见分析。

本研究通过三个模型在两个项目中的实证观察，尝试填补这些空白。

# 第3章 实证观察：三种模型在两个项目中的行为差异

本章基于在 CSO-FORCS 和 WarehouseMS 两个项目中约 3 个月的实际开发经验，系统性地记录和分析了三种不同能力层级的 LLM 模型在规范遵循上的行为差异。

## 3.1 观察方法与数据来源

### 3.1.1 观察对象

三个模型按能力从高到低分为三个层级：

| 模型 | 能力层级 | 架构能力 | 实现能力 | 约束遵循 |
|------|----------|----------|----------|----------|
| Claude Opus 4.8 | 架构级 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ |
| DeepSeek 4.0 | 实现级 | ⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐ |
| 小米 MIMO 2.5 PRO | 辅助级 | ⭐⭐ | ⭐⭐⭐ | ⭐⭐ |

### 3.1.2 数据来源

观察数据来源于以下渠道：

- **AI 会话日志**：记录了每次 AI 交互的 Prompt、上下文加载的 spec.md 文件、AI 输出的代码。
- **人工审查记录**：开发者在代码审查中标记的规范违规实例，包括违规类型、严重程度、关联的 spec.md 规则。
- **spec.md 更新历史**：通过 Git 追踪 spec.md 文件的变更，关联到触发变更的具体 AI 交互。
- **工具扫描报告**：spec_md_manager_v2.py 的 scan 和 report 输出，反映 spec.md 的覆盖度和信息密度变化。

### 3.1.3 分析框架

构建了四维度的模型能力-规范遵循分析模型：

- **抽象约束理解**：模型能否将 spec.md 中的原则性语句（如"禁止 Service 层跨系统调用"）转化为具体的设计决策？
- **多约束并发遵循**：当 spec.md 包含多条约束时，模型是否能够同时满足所有约束？
- **长会话约束保持**：在多轮对话中，模型的约束遵循度是否随时间衰减？
- **约束意图理解**：模型理解的是规则的字面意思还是规则的意图？

## 3.2 架构级模型（Claude Opus 4.8）的行为特征

### 3.2.1 优势领域

**抽象约束理解能力强**。当 spec.md 中写入"禁止 Service 层跨系统调用"这样的原则性约束时，Claude Opus 4.8 能够正确推导出具体的禁止行为列表——不仅不直接调用其他系统的 Service，还会识别出通过共享 DTO、共享静态配置等间接耦合路径。

**能够发现约束之间的矛盾**。在一个实例中，spec.md 第 3 章禁止"Web 层直接操作 EF Core"，第 5 章允许"在 Critical 场景下做性能优化"。Claude Opus 4.8 主动指出两者的潜在冲突：如果性能优化的唯一手段是绕过 EF Core 的变更追踪（使用 FromSqlRaw），这实质上是绕过了禁止操作的约束。它建议在 spec.md 中明确"性能优化"的允许边界——这种主动发现约束矛盾的能力，是中弱模型完全不具备的。

**长会话约束保持稳定**。在 10 轮以上的架构设计会话中，Claude Opus 4.8 的约束遵循度几乎不衰减。即使对话中引入了大量新信息，架构级约束（如分层依赖方向）始终保持正确。

### 3.2.2 风险领域

**对 spec.md 的过度信任**。Claude Opus 4.8 的高效遵循能力是一把双刃剑——如果 spec.md 本身包含错误约束，它同样会高效地执行。在 v2 第 5.2 节分析的"错误约定毒性"场景中，强模型实际上放大了错误的传播速度：一条错误规则在被质疑和修正之前，已经被强模型在多个文件和模块中高效地实现了。

**不必要的微观遵循**。对于明确标注了 `[confidence:preventive]` 的低可信度约束（如"优先使用 LINQ 而非 foreach"），Claude Opus 4.8 仍然倾向于严格遵守，即使在性能敏感的代码路径中也不例外。这表明即使有了可信度标注，强模型的"过度遵循"倾向仍然需要额外的机制来约束。

## 3.3 实现级模型（DeepSeek 4.0）的行为特征

### 3.3.1 优势领域

**具体约束遵循良好**。对于操作性的、可立即验证的约束（如"异步方法必须以 Async 结尾"、"禁止在 .razor 文件中写 `<style>`"），DeepSeek 4.0 的遵循率与 Claude Opus 4.8 基本持平。

**在约束充分的情况下，实现质量接近架构级模型**。当 spec.md 中的约束足够具体（"指名道姓"式而非"原则"式），DeepSeek 4.0 生成的代码在架构合规性上与 Claude Opus 4.8 的差异主要在于代码优雅度而非正确性。

### 3.3.2 劣势领域

**抽象约束的降级理解**。对于原则性约束，DeepSeek 4.0 倾向于理解字面意思而非意图。"禁止 Web 层直接操作 DbContext"被理解为"不能在 Web 层写 `_dbContext.Materials.Where(...)`"，但未被进一步推论为"所有数据访问必须通过 Service 层"。实践中观察到的结果是：DeepSeek 4.0 可能会在 Web 层的代码中通过一个薄包装（如直接在 razor.cs 中注入 Repository）间接操作数据——形式上没有直接使用 DbContext，但实质上违反了分层原则。

**约束遗漏**。当 spec.md 包含 5 条以上约束时，DeepSeek 4.0 会"选择性遗忘"。一个典型实例：在执行一个 Service 方法的修改任务时，spec.md 包含 6 条约束。审查发现，DeepSeek 4.0 遵循了其中 4 条（命名规范、异步模式、日志记录、错误处理），遗漏了 2 条（禁止在 Service 中直接使用 HttpContext、禁止硬编码配置值）。遗漏的 2 条恰好是 spec.md 中位置靠后且在生成代码的上下文中未触发"主动回忆"的约束。

**长会话约束衰减**。这是 DeepSeek 4.0 最显著的行为特征。统计数据（基于 20+ 次多轮会话的人工审查）：

| 会话轮次 | 约束遵循率 |
|----------|-----------|
| 第 1-3 轮 | 约 85-90% |
| 第 4-6 轮 | 约 70-80% |
| 第 7+ 轮 | 约 50-65% |

衰减的主要原因是会话 token 的增长稀释了 spec.md 内容在上下文中的"注意力权重"。当会话超过 10KB tokens 后，早期注入的 spec.md 约束在后续 token 的"冲击"下被逐渐边缘化。

### 3.3.3 spec.md 作为"能力放大器"

一个重要的发现是：spec.md 对 DeepSeek 4.0 的"能力放大"效果显著高于对 Claude Opus 4.8 的效果。基于审查记录的不完全统计：

- 无 spec.md 时，DeepSeek 4.0 的架构违规率约 30-40%
- 有 spec.md 时，架构违规率降至约 10-15%
- 经过 3 轮"违规 → 审查 → 更新 spec.md → 再次生成"的迭代后，降至约 5%

相比之下，Claude Opus 4.0 由于自身架构能力已经较强，spec.md 带来的边际改进较小（从约 15-20% 降至 5-8%）。

## 3.4 辅助级模型（小米 MIMO 2.5 PRO）的行为特征

### 3.4.1 行为特征

**外部 spec.md 的有效读取率极低**。小米 MIMO 2.5 PRO 在对话开始时被注入 spec.md 内容后，其后续生成行为与未注入时的差异在统计上不显著。这意味着该模型可能未能将 spec.md 的内容"内化"为生成代码时的约束——它"读"了但"没用"。

**约束遗忘速度极快**。即使在同一轮对话中，前半段声明的约束在后半段就可能失效。一个典型案例：在同一轮对话中，先要求"创建一个 MaterialDTO 类，包含所有 Material 实体的属性"，再要求"移除 MaterialDTO 中的 Id 字段，因为 DTO 不应暴露数据库主键"。模型执行了第二条指令，但在创建输出时重新引入了 Id 字段。

**多约束并发不可行**。当 Prompt 中包含 3 条以上约束时，小米 MIMO 2.5 PRO 几乎无法同时满足——它倾向于遵循最后一条或最具体的一条，而忽略其余。

### 3.4.2 有效使用策略

基于反复试验，以下策略对辅助级模型有效：

- **内联约束**：不依赖外部 spec.md，将约束直接写入 Prompt
- **原子约束**：一次只给一条约束。如果要满足 3 条约束，分 3 次交互完成
- **正例驱动**：不只是说"不要做什么"，要给出"应该怎么做"的完整代码模板
- **即时验证**：每轮输出后立即用强模型逐条检查是否满足约束

## 3.5 跨模型对比总结

### 3.5.1 约束遵循能力矩阵

| 能力维度 | Claude Opus 4.8 | DeepSeek 4.0 | 小米 MIMO 2.5 PRO |
|----------|:---:|:---:|:---:|
| 抽象约束理解 | ★★★★★ | ★★★ | ★ |
| 具体约束遵循 | ★★★★★ | ★★★★ | ★★ |
| 多约束并发（≥5条） | ★★★★★ | ★★★ | ★ |
| 长会话保持（10轮+） | ★★★★★ | ★★★ | ★ |
| 约束意图理解（vs字面） | ★★★★ | ★★ | ★ |
| 约束矛盾发现 | ★★★★ | ★ | — |
| spec.md 边际受益 | ★★ | ★★★★★ | ★ |

### 3.5.2 核心发现

1. **规范体系不是模型无关的**。规范的效果在很大程度上取决于执行规范的模型。同一份 spec.md，在不同模型上的有效利用率可能从接近 0%（辅助级）到接近 100%（架构级）。

2. **"能力放大"效应在中等模型上最显著**。对架构级模型，spec.md 是"锦上添花"；对实现级模型，spec.md 是"雪中送炭"；对辅助级模型，spec.md 是"对牛弹琴"。

3. **抽象约束 vs 具体约束的分野是关键的断层线**。所有模型都能较好地遵循具体约束（如命名规则）。抽象约束（如架构原则）的遵循能力随模型能力急剧下降——这定义了规范体系设计的核心挑战：如何在保持约束正确性的同时，使其可被不同能力的模型执行。

# 第4章 模型感知的规范设计策略

基于第3章的实证观察，本章提出一套系统性的模型感知规范设计策略。核心原则是：**规范密度应与模型能力反向匹配**——模型越弱，规范越要细、越少、越具体；模型越强，规范可以越粗、越多、越抽象。

## 4.1 核心原则：规范密度与模型能力反向匹配

### 4.1.1 原理推导

这一原则来源于信息论的基本逻辑：规范的目的是向模型传递"应该怎么做"的信息。强模型有较强的推理能力——它可以从少量的原则性信息中推导出大量的具体行为。弱模型推理能力有限——它需要的不是原则，而是精确到每一步的操作指令。

因此：
```
强模型（架构级）→ 粗粒度规范 → 全项目级 242 行 → 2-3 条核心约束 → 原则性表述
中模型（实现级）→ 中粒度规范 → 每文件 30-80 行 → 3-5 条具体约束 → 操作性表述
弱模型（辅助级）→ 细粒度规范 → Prompt 内联 → 1 条原子约束 → 代码模板式表述
```

### 4.1.2 反向匹配的实证依据

第3章的数据支持这一原则：

- Claude Opus 4.8 在 CSO-FORCS 的 242 行架构总纲下表现良好——它能将抽象约束正确转化为设计决策。
- DeepSeek 4.0 在架构总纲中受益，但其遵循度在文件级 spec.md（具体约束）上明显高于架构总纲（抽象约束）。
- 小米 MIMO 2.5 PRO 在任何形式的独立 spec.md 文件下均无明显受益——约束必须内联到 Prompt 中才有效。

## 4.2 分层约束表述：同一规则，三种写法

### 4.2.1 设计方法

对于同一条规范约束，应为不同能力层级的模型准备不同程度的表述。以"禁止 Web 层直接操作 DbContext"为例：

| 目标模型 | 表述类型 | 具体表述 |
|----------|----------|----------|
| Claude Opus 4.8 | **原则性表述** | "Web 层禁止直接依赖 DbContext，所有数据访问必须通过 Core 层 Service" |
| DeepSeek 4.0 | **操作性表述** | "不要在 .razor.cs 中写 `_dbContext.Materials.Where(...)`，改用 `IMaterialService.GetMaterialsAsync()`" |
| 小米 MIMO 2.5 PRO | **模板式表述** | "在 .razor.cs 中，移除所有 _dbContext 引用，替换为 IMaterialService 调用。示例：`var list = await MaterialService.GetMaterialsAsync()`" |

### 4.2.2 表述层次的递进逻辑

三种表述之间存在递进的"操作化"逻辑：

- **原则性表述**只说明"禁止做什么"和"应该通过什么途径做"，依赖模型的推理能力来填补"具体怎么实现"的空白。
- **操作性表述**给出了禁止的具体语法形式（"_dbContext.Materials.Where"）和允许的具体替代方案（"IMaterialService.GetMaterialsAsync"），但不提供完整的代码上下文。
- **模板式表述**提供了完整的代码示例，模型只需做文字替换即可——不依赖任何推理能力。

### 4.2.3 表述层次与模型能力的匹配规则

| 规则类型 | 架构级模型 | 实现级模型 | 辅助级模型 |
|----------|-----------|-----------|-----------|
| 架构约束（依赖方向、分层） | 原则性 | 操作性 | 模板式 |
| 命名规范 | 原则性 | 原则性 | 操作性 |
| 代码模式（错误处理、日志） | 原则性 | 操作性 | 模板式 |
| 禁止性约束（安全、连接管理） | 操作性 | 模板式 | 模板式 |
| 业务规则（状态转换、校验） | 原则性 + 操作 | 操作性 | 模板式 |

安全相关的约束（如"禁止 new HttpClient()"）对所有模型层级都至少使用操作级表述——因为安全违规的代价太高，不应依赖模型的推理能力来规避。

## 4.3 约束数量与能力匹配的"魔法数字"

### 4.3.1 实证得出的推荐约束数量

基于第3章的观察数据：

| 模型层级 | 推荐单文件约束数 | 原因 |
|----------|:---:|------|
| 架构级 | 无硬性限制 | 强模型能同时处理多条约束，WoWarehouseMS 的 242 行架构总纲无问题 |
| 实现级 | ≤ 5 条 | 超过 5 条后，遗漏率从 ~10% 升至 ~40% |
| 辅助级 | 1 条 | 超过 1 条后，无法同时满足。多条约束需分次交互 |

### 4.3.2 "约束衰减曲线"与重复注入策略

对于实现级模型（DeepSeek 4.0），长会话中的约束遵循度衰减是一个可量化的现象。对抗衰减的有效策略是**重复注入**——在每轮对话开始时，以压缩形式重申当前任务的 2-3 条核心约束。

实践中验证的策略：

```
第 1 轮：完整加载 spec.md（30-80 行）
第 2-3 轮：在 Prompt 开头插入 3 行"本轮约束摘要"
第 4+ 轮：如果会话超过 10KB tokens，建议开启新会话重新加载 spec.md
```

## 4.4 模型感知的验证强度

### 4.4.1 验证策略与模型能力的匹配

验证闭环的设计同样需要考虑模型能力差异：

| 模型层级 | 验证策略 | 验证工具 | 检查频率 |
|----------|----------|----------|----------|
| 架构级 | 抽样审查 | 人工 + Roslyn Analyzer | 关键模块 |
| 实现级 | 逐文件审查 | AI Agent + Roslyn Analyzer | 每次提交 |
| 辅助级 | 逐次生成后立即审查 | AI Agent | 每次生成 |

对辅助级模型，验证是最重的——因为其输出最不可信，每条生成都需要立即用强模型检查。对架构级模型，验证是抽样的——因为它"通常正确"，审查资源应集中在它可能出错的地方（如对低可信度规范的过度遵循）。

### 4.4.2 spec-tools 中的模型感知验证

本研究的 spec-tools 工具链已初步支持模型感知的验证策略：

- `SpecComplianceAnalyzer` 的 Roslyn 规则对**所有模型层级**的代码输出均生效——编译时检查不区分代码是由哪个模型生成的。
- `spec_compliance_check.py` 的 AI 审查 Agent 可以根据 `--model` 参数调整审查深度：对辅助级模型输出使用更详尽的审查清单。
- `spec_review_reminder.py` 的审查提醒可以按 spec.md 中标注的 `[min-model]` 过滤——如果一个规范只适用于架构级模型，但实际在实现级模型的代码中被引用了，应触发提醒。

## 4.5 在 spec.md 中嵌入模型感知元数据

### 4.5.1 最低模型要求标注

在 spec.md 中增加 `[min-model]` 标注，指明每条约束适用的最低模型层级：

```markdown
### 🚫 [min-model:deepseek-4.0] [confidence:validated] 分层架构红线
> 此规则需要模型能够理解"依赖方向"的抽象概念
> 辅助级模型可能无法正确遵循此规则，需要模板式表述
1. **禁止** Web 项目引用 Infrastructure 项目

### 🚫 [min-model:any] [confidence:consensus] 异步方法命名
> 此规则是简单的模式匹配，任何模型均可遵循
2. 异步方法必须以 Async 结尾
```

这使工具链和开发者能够根据当前使用的模型，自动筛选可用的约束集合。

### 4.5.2 模型降级策略表

当目标模型能力不足时，自动激活降级策略：

| 模型等级 | spec.md 加载策略 | 提示策略 | 验证策略 |
|----------|------------------|----------|----------|
| 架构级 | 完整加载 spec.md 树 | 标准 Prompt | 抽样审查 |
| 实现级 | 文件级 spec.md + 架构总纲摘要（≤5 条核心约束） | Prompt 首段重申 3 条核心约束 | 逐文件审查 |
| 辅助级 | 不加载外部 spec.md | Prompt 内联所有约束（原子化） | 逐次生成 → 逐次审查 |

## 4.6 讨论：实践者的选择框架

对于一个正在建立 AI 辅助开发规范体系的团队，本章的发现为以下决策提供了依据：

1. **首先评估你的模型**。在写规范之前，先用一组标准任务测试你的模型对规范的遵循能力。测试集应包括：抽象约束的遵循（如"禁止跨层调用"）、多约束并发（同时给 5 条约束）、长会话保持（5 轮后检查）。

2. **根据评估结果选择规范粒度**。如果模型是架构级，规范可以写成原则性指南；如果是实现级，规范必须写成操作性指令。

3. **为每个模型层级准备不同的约束表述**。不要把"写给 Claude"的 spec.md 原封不动地喂给 DeepSeek——需要一份"降级版本"。

4. **验证强度匹配模型能力**。不是所有模型输出都值得相同的审查投入——辅助级模型的每次输出都需要审查，架构级模型可以抽样。

# 第5章 混合流水线与元 Skills 框架

第4章提出了模型感知的规范设计策略，本章进一步回答两个相关的问题：（1）如何将不同能力的模型组织成一个协同工作的混合流水线？（2）如何管理规范体系自身的演化——即关于"如何管理规范体系"的元技能（Meta-Skills）？

## 5.1 混合流水线的架构设计

### 5.1.1 设计目标

混合流水线的核心目标是在充分利用各模型能力优势的同时，确保规范约束在流水线中一致传播。具体而言：

- **强模型做决策**，确保规范本身不引入错误
- **中模型做实现**，在强模型设定的约束下高效生成代码
- **弱模型做原子任务**，仅在最简单的场景下使用
- **审查由强模型完成**，形成质量闭环

### 5.1.2 流水线架构

```

│                        输入：用户需求                             │

│  • 分析需求 → 设计架构方案                                        │
│  • 将方案写入架构总纲.spec.md                                     │
│  • 识别关键约束 → 标注 [min-model] 和 [confidence]               │

                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│  阶段2: 任务拆解（Claude Opus 4.8）                               │
│  • 将架构方案拆解为具体实现任务                                     │
│  • 为每个任务附上适用的约束集（模型感知表述）                        │
│  • 决定每个任务分配给哪个模型层级                                   │
└─────────────────────────────────────────────────────────────────┘
                              │
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
┌─────────────────┐ ┌─────────────────┐ ┌─────────────────┐

              │               │               │
              └───────────────┼───────────────┘

┌─────────────────────────────────────────────────────────────────┐
│  阶段4: 代码审查（Claude Opus 4.8）                               │
│  • 逐文件检查是否符合架构总纲约束                                   │
│  • 对实现级模型输出：完整审查                                       │
│  • 对辅助级模型输出：每行审查                                       │
│  • 发现违规 → 记录到 spec.md 的"踩过的坑"                          │
│  • 发现约束不充分 → 更新 spec.md 增加约束                          │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│  输出：可合并的代码 + 更新的 spec.md                                │
└─────────────────────────────────────────────────────────────────┘
```

### 5.1.3 关键设计决策

**决策一：架构方案和 spec.md 必须由最强模型生产**

这是混合流水线中最重要的设计约束。如果 spec.md 由中弱模型编写，可能引入第 5.2 节分析的"错误约定"——而错误约定在混合流水线中会被多个模型并行传播，危害更大。在实践中的规则是：spec.md 的创建和修改（包括可信度标注、审计追踪、Sunset 设置）必须由架构级模型执行，实现级和辅助级模型绝对不应参与 spec.md 的编写。

**决策二：任务分配矩阵**

| 任务类型 | 架构级 | 实现级 | 辅助级 |
|----------|:---:|:---:|:---:|
| 架构设计 | ✅ 主责 | ⚠️ 仅审查 | ❌ 禁止 |
| 子系统边界定义 | ✅ 主责 | ⚠️ 仅审查 | ❌ 禁止 |
| Service 实现 | ✅ 可行 | ✅ 主责 | ⚠️ 简单 Service |
| Repository 实现 | ✅ 可行 | ✅ 主责 | ⚠️ 简单 CRUD |
| Entity / DTO 定义 | ✅ 可行 | ✅ 可行 | ✅ 主责 |
| 枚举定义 | ✅ 可行 | ✅ 可行 | ✅ 主责 |
| 复杂 Blazor 页面 | ✅ 主责 | ⚠️ 需要审查 | ❌ 禁止 |
| 简单 Blazor 页面 | ✅ 可行 | ✅ 可行 | ⚠️ 模板型 |
| spec.md 编写 | ✅ 主责 | ❌ 禁止 | ❌ 禁止 |
| 代码审查 | ✅ 主责 | ⚠️ 辅助审查 | ❌ 禁止 |
| 代码重构 | ✅ 主责 | ⚠️ 仅局部 | ❌ 禁止 |

**决策三：约束在模型间的一致性传递**

当强模型设计的约束需要被中模型执行时，约束不能直接"原样传递"——必须进行表述层次的降级。例如，Claude Opus 4.8 在架构总纲中写入的原则性约束：

> "禁止 Service 层跨系统调用"

在分配给 DeepSeek 4.0 的执行任务中，应降级为操作性表述：

> "在 WorkloadService 中，不要注入或调用 IMaterialService、IStockService、IAuthService。如需跨系统数据，通过 IIntegrationService 的标准化接口获取。"

这个降级过程由架构级模型在"阶段2：任务拆解"中完成。

## 5.2 元 Skills 框架

### 5.2.1 什么是元 Skills

v2 和 v3 前几章的分析揭示了一个更深层的问题：**规范体系本身需要被管理**。当前的 Skills 和 spec.md 体系聚焦于"如何管理代码"，但缺乏"如何管理规范体系本身"的方法论。

元 Skills 就是关于**规范体系自身的技能**——如何提取有价值的规范、如何判断规范是否过时、如何发现规范之间的矛盾、如何量化规范体系的健康度。

在 WarehouseMS 的 28 个已提取 Skills 中，仅有 5-8 个属于真正的原创贡献（spec.md 体系、架构总纲、踩坑记录等），其余 20+ 个属于 .NET 社区的标准实践（Repository 模式、Unit of Work、命名约定等）。将工业标准包装为"发现的 Skills"不仅会损害论文的可信度，更遮蔽了真正的创新所在——**元 Skills 才是规范体系方法论的核心贡献**。

### 5.2.2 六个元 Skills

| 元 Skill | 描述 | 核心问题 |
|----------|------|----------|
| **S1: Skills 提取方法论** | 如何从项目中系统性地提取可复用的 Skills | 如何区分"值得提取的 Skills"和"不值得提取的噪音"？ |
| **S2: Skills 价值评估** | 如何区分原创贡献与工业标准 | 这条 Skill 是我们发现的还是 .NET 社区早就知道的？ |
| **S3: Skills 过期检测** | 如何发现 Skills 已经过时 | 这条 Skill 描述的实践是否已被更新的技术取代？ |
| **S4: Skills 矛盾检测** | 如何发现两个 Skills 互相矛盾 | Skill A 说"禁止 X"，Skill B 说"在 Y 场景下可以 X"——谁是优先的？ |
| **S5: AGENTS.md 设计决策框架** | 何时用精简索引（82行），何时用完整手册（303行） | AGENTS.md 应该是"导航地图"还是"完整手册"？ |
| **S6: spec.md 健康度评分** | 如何量化 spec.md 体系的健康状态 | 这个项目的 spec.md 体系是"健康的"还是"退化的"？ |

### 5.2.3 元 Skills 与 spec-tools 的对应关系

元 Skills 不仅是方法论概念，已有对应的工具实现：

| 元 Skill | 对应工具 | 实现状态 |
|----------|----------|:---:|
| S1: 提取方法论 | `spec_deploy_init.py`（智能扫描 + --smart 模式） | ✅ |
| S2: 价值评估 | `spec_md_manager_v2.py report --density`（信息密度覆盖度） | ✅ |
| S3: 过期检测 | `spec_md_manager_v2.py review --stale-days` + `spec_review_reminder.py` | ✅ |
| S4: 矛盾检测 | `spec_impact_analyzer.py`（引用链追踪可间接发现矛盾） | △ |
| S5: AGENTS.md 设计框架 | `deploy.sh`（注入标准化 spec.md 规则到 AGENTS.md） | ✅ |
| S6: 健康度评分 | `spec_md_manager_v2.py report --density`（空壳率 + 信息密度） | △ |

△ 表示功能部分实现，需进一步开发。

### 5.2.4 元 Skills 的学术意义

在论文中讨论 Skills 时，正确的叙事不是"我们提取了 28 个 Skills，其中 18 个高可复用"，而是：

> "我们尝试从两个工业项目中提取可复用的 AI 辅助开发 Skills。过程中发现了一个关键挑战：如何区分'值得提取的通用技能'和'项目特定的实现细节'。我们提出了一个三级分类框架（原创/创新应用/工业标准），并发现仅有 5/28 的 Skills 属于真正的原创贡献。更重要的是，我们发现 Skills 体系本身需要一套元 Skills 来维持其健康性，并提出了 6 个元 Skills。"

## 5.3 混合流水线的实证效果

### 5.3.1 在 CSO-FORCS 项目上的应用

CSO-FORCS 项目采用混合流水线进行了约 3 个月的实际开发。分工模式为：

- Claude Opus 4.8 负责架构设计、spec.md 编写、代码审查
- DeepSeek 4.0 负责 70% 的业务逻辑实现
- 小米 MIMO 2.5 PRO 负责 Entity、DTO、Enum 等简单数据类

### 5.3.2 效果观察

**代码审查中的违规发现**：
- DeepSeek 4.0 实现中发现的违规经过 2-3 轮"审查 → 更新约束 → 重新实现"迭代后，65% 的违规不再复现。
- 25% 的违规需要将约束从原则性表述升级为操作性表述才能被 DeepSeek 4.0 正确执行。
- 10% 的违规属于"系统性违规"——DeepSeek 4.0 在该类约束上的遵循能力不足，该模块被转为由 Claude Opus 4.8 实现。

**成本效益**：
- 约 70% 的代码行由 DeepSeek 4.0 生成，20% 由 Claude Opus 4.8 生成，10% 由小米 MIMO 2.5 PRO 生成。
- Claude Opus 4.8 的使用集中在高价值任务（架构、审查、关键模块），避免了在简单任务上的成本浪费。
- 与纯 Claude Opus 4.8 方案相比，混合流水线约降低了 40% 的模型调用成本，且未显著降低代码质量（架构审查通过率差异 < 5%）。

### 5.3.3 局限与注意事项

1. **审查工作不可省略**。混合流水线的前提是强模型执行审查。如果省略审查步骤，违规代码将直接进入代码库。
2. **约束降级需要架构级模型主动执行**。目前降级过程依赖开发者或架构级模型手动完成，尚未自动化。
3. **模型切换成本**。不同模型的 API 和交互方式不同，混合使用的实际便利性受工具链成熟度影响。

# 第6章 结论与展望

## 6.1 研究总结

本研究（v3）在前两个版本的基础上，引入了"LLM 模型能力"这一被忽视的变量，对 AI 辅助开发规范体系的效果进行了条件性分析。核心发现可以概括为三个层次：

### 6.1.1 模型能力是规范体系效果的独立变量

v1 假设"规范写得好，AI 就能遵循"；v2 发现"规范写得好，AI 也可能遵循不了"（验证闭环缺失）；v3 进一步发现"AI 能不能遵循规范，很大程度上取决于是哪个 AI"。

第3章的实证观察清晰地展示了这一差异：同一套 spec.md 体系，在 Claude Opus 4.8 上可以有效转化为架构约束，在 DeepSeek 4.0 上需要操作性表述才能执行，在小米 MIMO 2.5 PRO 上几乎完全无效——除非约束被内联到 Prompt 中。

这一发现意味着，任何对 AI 辅助开发规范体系的讨论都必须附带"目标模型"这一前置条件。脱离模型能力谈"规范体系的效果"是没有意义的。

### 6.1.2 模型感知的规范设计策略

基于"规范密度与模型能力反向匹配"的核心原则，本研究提出了：

- **分层约束表述**：同一条规则，对架构级/实现级/辅助级模型分别采用原则性/操作性/模板式三种表述。
- **约束数量匹配**：实现级模型单文件 ≤ 5 条，辅助级模型一次仅 1 条。
- **重复注入策略**：对抗实现级模型的长会话约束衰减。
- **验证强度匹配**：辅助级模型输出逐次审查，架构级模型输出抽样审查。

### 6.1.3 混合流水线与元 Skills

- **混合流水线**：强模型决策（架构 + spec.md）→ 中模型实现 → 弱模型原子任务 → 强模型审查。实证显示可降低约 40% 的模型调用成本。
- **元 Skills 框架**：6 个元 Skills 填补了"如何管理规范体系"的方法论空白。规范体系的管理本身需要一个方法轮。

## 6.2 v1 → v2 → v3 的演化逻辑

三个版本的论文递进构成了一个完整的认知演化：

```
v1（描述性）→ v2（批判性）→ v3（条件性）

"我们建立了一套规范体系"  →  "这个体系有问题"  →  "问题的大小取决于用哪个模型"
"83.3% 的完整性"       →  "7个弊端+2个缺陷" →  "模型能力分层决定规范效果"
"如何建立"              →  "出了什么问题"     →  "在什么条件下有效"
```

这一演化逻辑本身反映了对复杂工程问题认识的深化：从简单的"解决方案"到"问题分析"，再到理解解决方案的边界条件。

## 6.3 对工业实践的启示

### 6.3.1 给正在使用 AI 编码助手的团队

1. **不要假设所有模型的"理解能力"相同**。你为 Claude 写的 spec.md，DeepSeek 可能读不懂其中的抽象约束。
2. **测试你的模型**。在项目开始时，用一组标准任务测试你的模型对规范的遵循能力，根据结果决定规范风格。
3. **强模型管架构，中模型管实现**。这是目前性价比最高的分工模式。
4. **不要让中弱模型写 spec.md**。错误约定的传播成本在混合流水线中更高。

### 6.3.2 给 AI 编码工具开发者

1. **在工具中内置模型感知的约束传递**。工具应该知道当前使用的是哪个模型，并自动调整约束的呈现粒度。
2. **支持"降级表述"的自动生成**。当开发者用原则性语言写了一条约束，工具应能自动生成操作性和模板式的降级版本。
3. **在工具中内建审查能力**。AI 编码工具不仅是"代码生成器"，也是"代码审查器"——审查功能应该在生成时就可用。

## 6.4 研究局限

1. **观察的非受控性**。本研究的实证数据来自实际开发活动，而非受控实验。模型间的能力差异可能与其他混淆变量（任务复杂度、开发者参与度、会话长度）交织。

2. **模型版本的快速迭代**。本文分析的三个模型的行为特征可能随模型更新而变化。DeepSeek 4.0 的下一个版本可能在抽象约束理解上有显著提升，从而使本文的部分发现过时。

3. **样本量有限**。观察基于两个 C#/Blazor 项目，模型行为可能受编程语言和技术栈影响。

4. **元 Skills 的验证不充分**。六个元 Skills 中仅 S1-S3 和 S5 有工具实现和初步使用数据，S4（矛盾检测）和 S6（健康度评分）仍处于概念阶段。

## 6.5 未来工作

### 6.5.1 模型能力基线测试

开发一套标准化的"规范遵循能力测试集"，使团队在项目开始前能快速评估其使用的模型在哪类规范的遵循上存在风险。测试集应包括抽象约束、具体约束、多约束并发、长会话衰减等维度。

### 6.5.2 约束表述的自动降级

目前约束降级（原则性 → 操作性 → 模板式）依赖人工或架构级模型手动完成。探索是否可以使用架构级模型自动生成降级版本——即"用强模型为弱模型准备约束"。

### 6.5.3 模型切换时的约束传播验证

当流水线中的模型发生切换（如 DeepSeek 4.0 升级为更高版本或替换为其他模型），需要自动验证新模型对现有 spec.md 体系的遵循能力是否退化。

### 6.5.4 元 Skills 的完整工具化

将 S4（矛盾检测）和 S6（健康度评分）从概念发展为可工作的工具，使规范体系的健康管理完全自动化。
