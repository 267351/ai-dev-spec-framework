# LLM 模型差异对 spec.md 体系效果的影响分析

> 基于两个项目的实际开发经验，使用三种不同能力层级的大模型（国产小米 MIMO 2.5 PRO、
> DeepSeek 4.0，以及 Anthropic Claude Opus 4.8）的对比观察，分析模型能力差异如何影响
> AI 辅助开发规范体系的有效性，以及针对弱模型的补偿策略。

---

## 一、实际使用的模型与角色分工

| 模型 | 角色 | 架构能力 | 实现能力 | 约束遵循 |
|------|------|----------|----------|----------|
| **Claude Opus 4.8** | 搭架构 / 核心决策 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ |
| **DeepSeek 4.0** | 日常开发 / 功能实现 | ⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐ |
| **小米 MIMO 2.5 PRO** | 辅助编码 / 简单任务 | ⭐⭐ | ⭐⭐⭐ | ⭐⭐ |

**实践中形成的分工模式**：
- Claude Opus 4.8 负责架构设计和关键模块（如分层方案、子系统边界、HAL 抽象层）
- DeepSeek 4.0 负责主体业务逻辑的实现（Service、Repository、Controller）
- 小米 MIMO 2.5 PRO 在简单任务（DTO、Entity、Enum 定义）上使用

## 二、模型能力差异如何影响 spec.md 体系

### 2.1 强模型（Claude Opus 4.8）的表现

**优势**：
- 能够理解 spec.md 中的**抽象约束**（如"禁止 Service 层跨系统调用"），并将其转化为具体的设计决策
- 能够主动发现 spec.md 中**矛盾的或隐含的约束**，并提出修正建议
- 在架构总纲级别的决策中，能够**权衡多个约束之间的冲突**
- 生成的代码与 spec.md 的**匹配度高**，人工审查发现的违规少

**spec.md 体系对强模型的边际价值**：
- 架构总纲.spec.md 对强模型价值**高**——强模型能把抽象约束转化为正确设计
- 文件级 spec.md 对强模型价值**中**——强模型可能不需要"禁止在 .razor 中写 `<style>`"这种级别的微观指导
- **风险**：强模型对 spec.md 的过度信任——如果 spec.md 有错误，强模型会非常高效地执行错误指令

### 2.2 中弱模型（DeepSeek 4.0）的表现

**优势**：
- 能够在给定明确约束时正确执行实现任务
- 对 spec.md 中**具体的、操作性的约束**遵循较好（如"异步方法以 Async 结尾"）

**劣势**：
- 对**抽象约束**的理解有降级——可能在"禁止 Service 跨系统调用"的约束下，仍然间接地通过共享 DTO 产生耦合
- **约束遗漏**：当 spec.md 有 5 条约束时，可能只遵循了 3 条，另外 2 条被忽略
- **约束扭曲**：理解规则的字面意思但误解意图。例如"禁止 Web 层直接操作 DbContext"→ 理解为"可以在 Web 层通过 Repository 操作"，而非正确的"必须在 Service 层通过 Repository 操作"
- 在长时间会话中，**约束遵循度会衰减**——前 3 轮严格遵循，第 5 轮开始出现违规

**spec.md 体系对中弱模型的补偿需求**：
- 约束需要**更具体、更操作化**（"不要用抽象描述，要指名道姓"）
- 单一文件中的约束数量需要**更少**（≤5 条，多了会被忽略）
- 需要**重复注入**约束（不能只读一次 spec.md，每轮都要重申关键约束）

### 2.3 弱模型（小米 MIMO 2.5 PRO）的表现

**劣势**：
- 对 spec.md 的**有效读取率低**——可能读了但未内化
- **约束遗忘极快**——即使在同一轮对话中，前面说的约束后面就忘了
- **不能处理多约束并发**——当 spec.md 有 3 条以上约束时，无法同时满足
- **不能理解约束之间的优先级**——可能会为遵守一条次要约束而违反主要约束
- 架构级别的决策**几乎完全不可靠**——不能用于搭架构

**spec.md 体系对弱模型的效果**：
- 文件级 spec.md 的微观约束（如命名规范）**部分有效**
- 架构级 spec.md 的宏观约束（如分层架构）**基本无效**
- 踩过的坑记录**基本无效**——弱模型读不懂"为什么这个坑会发生"

**对弱模型的使用策略**：
- 仅用于定义明确的**原子任务**（如"创建一个 Material DTO 类"）
- 任务提示中要**内联约束**（不要把约束放在外部 spec.md，要直接写在 Prompt 里）
- 输出后需要**立即用强模型审查**

## 三、模型感知的 spec.md 设计策略

### 3.1 核心原则：规范密度应匹配模型能力

```
强模型（Claude Opus 4.8）：
  规范可以抽象、可以多 → "架构总纲.spec.md 可以写 242 行"
  规范可以依赖模型的判断力 → "允许模型在约束之间做出权衡"

中模型（DeepSeek 4.0）：
  规范必须具体、必须少 → "每条约束 ≤1 句话，每文件 ≤5 条约束"
  规范必须可操作 → "禁止 A 调用 B，使用 C 代替"（而不是"确保正确的依赖方向"）

弱模型（小米 M2.5 PRO）：
  规范必须内联 → "不要用 spec.md，直接写在 Prompt 里"
  规范必须原子化 → "一次只给一条约束"
  规范必须有验证 → "生成代码后，立即逐条检查是否满足"
```

### 3.2 分层约束强度

对不同能力的模型，同一规则应该有不同的表述方式：

**规则**："禁止 Web 层直接操作 DbContext"

| 目标模型 | 约束表述 | 原因 |
|----------|----------|------|
| Claude Opus 4.8 | "Web 层禁止直接依赖 DbContext，所有数据访问必须通过 Core 层 Service" | 给出原则，模型能推导具体实现 |
| DeepSeek 4.0 | "不要在 .razor.cs 中写 `_dbContext.Materials.Where(...)`，改用 `IMaterialService.GetMaterialsAsync()`" | 指名道姓，给出正例 |
| 小米 M2.5 PRO | "在 .razor.cs 中，移除所有 _dbContext 引用，替换为 IMaterialService 调用。示例：`var list = await MaterialService.GetMaterialsAsync()`" | 给出代码模板 |

### 3.3 模型感知的任务分配策略

```
                       Claude Opus 4.8          DeepSeek 4.0        小米 M2.5 PRO
                       ───────────          ────────────        ─────────────
架构设计                ✅ 主责              ⚠️ 仅审查           ❌ 禁止
子系统边界定义          ✅ 主责              ⚠️ 仅审查           ❌ 禁止
Service 实现            ✅ 可行              ✅ 主责              ⚠️ 简单 Service
Repository 实现         ✅ 可行              ✅ 主责              ⚠️ 简单 CRUD
Entity / DTO 定义       ✅ 可行              ✅ 可行              ✅ 主责
枚举定义                ✅ 可行              ✅ 可行              ✅ 主责
Blazor 页面（复杂）     ✅ 主责              ⚠️ 需要审查         ❌ 禁止
Blazor 页面（简单）     ✅ 可行              ✅ 可行              ⚠️ 模板型页面
spec.md 编写            ✅ 主责              ✅ 可行              ❌ 禁止（会写错）
spec.md 审查            ✅ 主责              ✅ 主责              ❌ 禁止
代码重构                ✅ 主责              ⚠️ 仅局部重构       ❌ 禁止
```

### 3.4 混合流水线

最优实践是使用**混合流水线**而非单一模型：

```
输入：用户需求
  ↓
阶段1: Claude Opus 4.8 → 设计架构方案 → 写入 架构总纲.spec.md
  ↓
阶段2: Claude Opus 4.8 → 拆解为具体任务 → 每个任务附带约束
  ↓  ┌─────────────────────────────────────────┐
阶段3:│ DeepSeek 4.0 → 实现 Service A            │
     │ DeepSeek 4.0 → 实现 Service B            │ ← 并行
     │ 小米 M2.5 PRO → 实现 简单 DTO            │
     └─────────────────────────────────────────┘
  ↓
阶段4: Claude Opus 4.8 → 审查代码是否符合架构方案
  ↓  ┌─────────────────────────────────────────┐
     │ 发现违规 → 记录到 spec.md 的"踩过的坑"    │
     │ 更新约束 → 下次任务带上更强的约束         │
     └─────────────────────────────────────────┘
  ↓
输出：可合并的代码 + 更新的 spec.md
```

**关键设计决策**：
- **架构方案**由最强模型产出，形成 spec.md 的核心内容
- **实现任务**分发到匹配模型能力的层次
- **审查工作**由最强模型完成，形成质量闭环
- **spec.md 本身**由最强模型编写和维护（防止错误约定被写入）

## 四、模型能力与 spec.md 体系的互相塑造

### 4.1 spec.md 是模型的"能力放大器"

对于 DeepSeek 4.0 这类中模型，spec.md 的存在可以将它的有效能力提升到接近 Claude Opus 4.8 的水平——因为它不需要自己推断架构约束，只需要遵循已经写好的约束。

**量化效果**：
- 无 spec.md 时，DeepSeek 4.0 生成的代码中架构违规率约 30-40%
- 有 spec.md 时，架构违规率降至约 10-15%
- 经过 3 轮"违规→审查→更新 spec.md→再次生成"的迭代后，降至约 5%

### 4.2 模型能力的下限决定了 spec.md 的设计上限

如果团队使用的模型是小米 MIMO 2.5 PRO，那么不能设计依赖于"模型能理解抽象约束"的 spec.md 体系。必须将 spec.md 设计为**极简的操作手册**而非**原则性指导**。

**这意味着**：
- spec.md 的可复用性取决于**目标模型的能力**
- 为 Claude Opus 4.8 设计的 spec.md 对小米 M2.5 PRO 可能无效
- spec.md 体系需要标注"最低模型要求"

### 4.3 spec.md 的粒度应该与模型能力反向匹配

```
强模型（Claude Opus 4.8）  →  粗粒度 spec.md  →  242 行架构总纲  →  2-3 条核心约束
中模型（DeepSeek 4.0）→  中粒度 spec.md  →  每文件 30-80 行  →  3-5 条具体约束
弱模型（小米 M2.5）    →  细粒度 spec.md  →  Prompt 内联       →  1 条原子约束
```

规律：**模型越弱，spec.md 越要写细；模型越强，spec.md 越要写粗**。

## 五、对 spec.md 体系的改进建议（模型感知版）

### 5.1 在 spec.md 中增加"最低模型要求"标注

```markdown
### 🚫 [min-model:deepseek-4.0] 分层架构红线
> 此规则需要模型能够理解"依赖方向"的抽象概念
> 小米 M2.5 PRO 级别的模型可能无法正确遵循此规则
1. **禁止** Web 项目引用 Infrastructure 项目

### 🚫 [min-model:any] 异步方法命名
> 此规则是简单的模式匹配，任何模型均可遵循
2. 异步方法必须以 Async 结尾
```

### 5.2 创建"模型降级策略"表

当目标模型能力不足时，自动激活降级策略：

| 模型等级 | spec.md 加载策略 | 提示策略 | 验证策略 |
|----------|------------------|----------|----------|
| 架构级（Claude Opus 4.8） | 完整加载 spec.md 树 | 标准 Prompt | 抽样审查 |
| 实现级（DeepSeek 4.0） | 加载文件级 spec.md + 架构总纲摘要 | Prompt 中重申 3 条核心约束 | 逐文件审查 |
| 辅助级（小米 M2.5 PRO） | 不加载外部文件 | Prompt 内联所有约束 | 逐次生成 → 逐次审查 |

### 5.3 设计"模型能力测试"基线

在项目初始化时，用一组标准任务测试模型对 spec.md 的遵循能力，根据测试结果选择 spec.md 的粒度和验证策略。测试集包括：
- 是否能正确遵循"禁止跨层调用"的约束？
- 在 5 轮对话后是否仍能记住约束？
- 是否能理解 spec.md 中"坑点"章节的语义？
