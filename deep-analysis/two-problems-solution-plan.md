# 两个重大问题的分析与解决方案计划

> 基于对 CSO-FORCS 和 WarehouseMS 中 .spec.md 体系的深度分析，
> 识别出两个关键的系统性缺陷，并制定解决方案。

---

## Problem 1：缺少 AI 生成代码是否符合 spec.md 的自动验证闭环

### 1.1 问题解释

**现状**：
```
AI 读取 spec.md → AI 生成代码 → [缺失] → 人工审查发现违规
```

当前流程依赖**人类的代码审查**来发现 AI 是否违反了 spec.md 的约束。但存在两个致命缺陷：

1. **审查者也是人，也会遗漏**：当 spec.md 有 100+ 个文件、每个文件有 3-8 条约束时，审查者不可能记住所有规则
2. **审查发生在事后**：代码已经写好、提交、甚至合并了，才发现违反了 spec.md——修复成本高

**具体场景举例**：

WarehouseMS `架构总纲.spec.md` 中有一条规则：
> **禁止** MaterialCategoryService 调用 IConversionEngine

这是一个**完全可以自动检查**的规则——静态分析 Service 类的依赖注入即可。但当前没有任何自动化工具来做这件事。

**"闭环"的含义**：
```
写入 spec.md 约束 → AI 生成代码 → 自动检查是否符合 → 不符合 → 拒绝/警告 → AI 修正
         ↑                                                              |
         └──────────────── 反馈更新 spec.md ←──────────────────────────┘
```

当前这个环是**断开的**——缺少自动检查和自动反馈两个环节。

### 1.2 规则的分类：哪些可自动验证，哪些不能？

| 类别 | 示例 | 自动验证可行性 |
|------|------|---------------|
| **架构依赖规则** | "禁止 Web 引用 DAL" | ✅ 高 - 检查 csproj ProjectReference |
| **命名规则** | "异步方法必须以 Async 结尾" | ✅ 高 - AST 分析或正则 |
| **DI 规则** | "Service 通过构造函数注入，禁止 new" | ✅ 中高 - Roslyn Analyzer |
| **模式规则** | "Controller 必须 try/catch + BadRequest" | ✅ 中 - AST 模式匹配 |
| **业务逻辑规则** | "发放砂轮片必须校验四层匹配" | ❌ 低 - 需要理解业务语义 |
| **安全性规则** | "禁止在日志中输出密码" | ⚠️ 中 - 静态分析部分可行 |
| **上下文规则** | "此方法仅在夜间批处理中调用" | ❌ 极低 - 纯语义 |

**关键结论**：约 60-70% 的 spec.md 约束属于"可自动验证"或"可部分自动验证"类别。目前这些全部依赖人工审查。

### 1.3 解决方案设计

#### 方案 A：基于 Roslyn Analyzer 的编译时验证（推荐）

**原理**：将 spec.md 中的机器可验证规则翻译为 Roslyn Analyzer（C# 编译器插件），在编译时自动检查。

**流程**：
```
spec.md 规则 → 规则解析器 → Roslyn Analyzer 代码生成 → 编译时自动检查
```

**优点**：
- 编译时即发现，零运行时开销
- IDE 中实时显示错误波浪线
- 可以阻止 CI 构建（`dotnet build` 失败即拒绝合并）

**缺点**：
- 需要为每个规则编写 Analyzer（开发成本）
- 只适用于机器可验证的规则
- 规则变更需要重新编译 Analyzer

**实现步骤**：
1. 从 spec.md 中提取可机器验证的规则
2. 设计规则 DSL 或标注格式（如在 spec.md 中使用 `[verifiable]` 标签）
3. 创建 Roslyn Analyzer 项目
4. 逐个实现规则
5. 集成到 CI/CD

#### 方案 B：基于 AI 的代码审查 Agent（补充方案）

**原理**：在代码提交前，使用独立的 AI Agent 读取 spec.md 并检查变更是否符合约束。

**流程**：
```
代码变更 + spec.md → AI 审查 Agent → 合规性报告 → 不合规项 → 自动拒绝或警告
```

**优点**：
- 可以覆盖语义规则（业务逻辑、上下文约束）
- 无需编写 Analyzer 代码
- 可以处理新的 spec.md 规则而不需要重新部署

**缺点**：
- AI 审查本身可能出错（误报/漏报）
- 每次审查消耗 tokens
- 依赖 AI 服务的可用性

**实现步骤**：
1. 设计 AI 审查 Prompt 模板
2. 集成到 Git Pre-Commit Hook 或 CI
3. 设计审查结果格式（通过/警告/拒绝）
4. 与人工审查流程对接

#### 方案 C：混合方案（推荐）

```
编译时（方案 A）：检查架构依赖、命名、DI 等结构化规则
  ↓ 通过
提交时（方案 B）：AI Agent 检查业务逻辑、上下文规则
  ↓ 通过
Code Review：人类审查最终的合规性报告
```

**工具链设计**：

```
dotnet build
  ├── Roslyn Analyzer: 依赖方向检查
  ├── Roslyn Analyzer: 命名约定检查
  └── Roslyn Analyzer: DI 注入检查
       ↓ 全部通过
python3 tools/spec_compliance_check.py --changed-files
  ├── 提取变更文件对应的 spec.md
  ├── AI Agent 审查变更是否符合约束
  └── 生成合规性报告 (JSON/Markdown)
       ↓ 输出
合规性报告:
  ✅ 通过: 12 条
  ⚠️ 警告: 2 条
  ❌ 违规: 1 条 → 拒绝合并
```

### 1.4 可验证规则标注格式设计

为了让自动验证工具能够解析 spec.md，设计一种**标注格式**：

```markdown
## 3. 禁止修改的内容（绝对不能动）

### 🚫 [verifiable:di] 分层架构红线
<!-- @rule id=WM-ARCH-001 type=dependency-check -->
<!-- @check: Web项目不引用Infrastructure项目 -->
1. **禁止** Web 项目直接操作 EF Core DbContext
<!-- @check: Web层不包含DbContext类型引用 -->

### 🚫 [verifiable:naming] 异常处理规范
<!-- @rule id=WM-CODE-001 type=ast-pattern -->
<!-- @pattern: Controller方法体必须包含 try/catch -->
2. Controller 必须 try/catch + BadRequest(ex.Message)
```

**标注类型**：
| 标注 | 含义 | 检查方式 |
|------|------|----------|
| `[verifiable:di]` | 依赖注入相关 | Roslyn 语义分析 |
| `[verifiable:naming]` | 命名规范 | 正则/AST 匹配 |
| `[verifiable:pattern]` | 代码模式 | AST 模式匹配 |
| `[contextual]` | 语义规则 | AI Agent 审查 |
| `[unverifiable]` | 不可自动验证 | 仅文档 |

### 1.5 验证闭环的完整数据流

```
┌─────────────────────────────────────────────────────────────┐
```

## Problem 2：错误约定的误导与修正困难

### 2.1 问题解释

**这是一个比 Problem 1 更根本、更危险的问题。**

**为什么危险？**

1. **Spec.md 具有"权威性"**——AI 将其视为绝对真理，不会质疑
2. **Spec.md 具有"传染性"**——一个错误的约束会导致所有基于它的代码都偏离正确方向
3. **Spec.md 具有"持久性"**——它被设计为"永久记录"，错误的记录也永久存在
4. **Spec.md 具有"隐形权威"**——后来的开发者不知道这条规则是"经验结晶"还是"某人的猜测"

**具体场景（真实可能发生）**：

WarehouseMS `架构总纲.spec.md` 中有一条：
> **禁止**在 `.razor` 文件中直接实例化 Service（必须通过 DI 注入）

这条规则本身是**正确的 good practice**。但假设有人写错了：

> **禁止**在 `.razor` 文件中使用任何 `@inject`（必须通过构造函数注入）

（这是错误的——Blazor 中 `@inject` 是官方推荐模式，构造函数注入在 Blazor 组件中不可行）

后果：
1. AI 读到这条规则后，拒绝在 `.razor` 文件中使用 `@inject`
2. 所有新开发的 Blazor 页面都采用错误的 Service 获取方式
3. 错误模式扩散到 20+ 个页面
4. 当有人发现 `@inject` 是正确做法时，需要修改 20+ 个文件
5. 但 spec.md 说"禁止"，修改者担心可能有隐藏原因而不敢改

**为什么"改回来很难"？**

| 障碍 | 原因 |
|------|------|
| **不知道影响范围** | 没有工具追踪"哪些代码是基于这条 spec 编写的" |
| **不知道写入理由** | 没有记录"为什么当时加了这条规则" |
| **害怕"有坑没被发现"** | 看到"永久记录"和"踩过的坑"标签，不敢轻易质疑 |
| **修正需要全面审查** | 改了 spec 后需要检查所有遵守旧 spec 的代码是否也需要改 |
| **团队认知惯性** | 大家都默认"spec 是对的"，质疑需要额外勇气 |

### 2.2 错误约定的生命周期

```
阶段1: 创建
  某开发者遇到问题 X，认为原因是 Y
  → 在 spec.md 中写入"禁止做 Y"
  → 但实际原因可能是 Z，而 Y 本身是合理的操作

阶段2: 固化
  AI 读到"禁止做 Y"，在所有相关代码中遵守
  → 形成新的代码模式
  → 新成员加入，看到这条规则，默认接受

阶段3: 传播
  其他 spec.md 文件引用这条规则
  → "参见架构总纲.spec.md §3：禁止做 Y"
  → 错误规则变成了"权威参考"

阶段4: 发现
  某资深开发者审查代码时发现 Y 应该是合理的
  → 但已经影响了 30+ 个文件
  → 改 spec 容易，改代码难

阶段5: 修正困境
  - 需要修改 spec.md（删除错误规则）
  - 需要审查所有遵守过这条规则的代码
  - 需要向团队解释"为什么之前错了"
  - 担心有隐藏的坑点被这条规则保护着
```

### 2.3 解决方案设计

#### 核心思路：在"永久记录"和"可能是错的"之间建立平衡

#### 措施一：Spec 可信度分级

在每条约束上标注**可信度等级**：

```markdown
## 3. 禁止修改的内容

### 🚫 [confidence:validated] 分层架构红线
> **可信度**: ⭐⭐⭐⭐⭐ (由 3 次生产事故验证)
> **验证记录**: 2026-04-08 循环依赖导致编译失败 | 2026-05-12 运行时 DI 崩溃
1. **禁止** Web 项目引用 Infrastructure 项目

### 🚫 [confidence:preventive] 异步方法命名
> **可信度**: ⭐⭐ (预防性规范，未发生过事故)
> **提出者**: @alice | **提出日期**: 2026-06-01
2. **建议** 异步方法使用 Async 后缀

### 🚫 [confidence:speculative] AI 代码风格偏好
> **可信度**: ⭐ (个人偏好，可讨论)
> **提出者**: @bob | **提出日期**: 2026-06-10
3. **建议** 优先使用 LINQ 而非 foreach
```

**可信度等级定义**：

| 等级 | 标识 | 含义 | 可质疑性 |
|------|------|------|----------|
| ⭐⭐⭐⭐⭐ | `validated` | 由实际事故验证，有明确证据 | 不可质疑（除非有新证据） |
| ⭐⭐⭐⭐ | `proven` | 在多项目中验证有效 | 需要充分理由 |
| ⭐⭐⭐ | `consensus` | 团队共识，基于经验 | 需要讨论 |
| ⭐⭐ | `preventive` | 预防性规则，未实际触发 | 可以质疑 |
| ⭐ | `speculative` | 个人偏好或实验性规则 | 鼓励质疑 |

#### 措施二：Spec 变更影响分析

设计一个工具，在修改 spec.md 前自动分析：

```bash
python3 tools/spec_impact_analyzer.py --spec 架构总纲.spec.md --rule "禁止Web引用Infrastructure"
```

输出：
```
📊 影响分析报告

规则：禁止 Web 项目引用 Infrastructure 项目
位置：架构总纲.spec.md §3 第一条
可信度：⭐⭐⭐⭐⭐ (validated - 3 次事故)

📁 依赖此规则的代码文件 (23 个)：
  src/WarehouseManagement.Web/Components/Pages/MaterialList.razor.cs
    → 此文件遵照此规则，未引用 Infrastructure

    → ...

📁 引用此规则的其他 spec.md (5 个)：
  src/WarehouseManagement.Web/Components/Pages/Warehouse/CategoryTree.spec.md
  → §3 引用了此规则
  → 修改此规则后，需要同步审查这 5 个 spec.md

  - 高风险: 3 个文件（架构核心约束）
  - 中风险: 15 个文件
  - 低风险: 5 个文件

📋 建议修改步骤：
  1. 更新架构总纲.spec.md

  3. 同步更新 5 个引用 spec.md
  4. 运行完整测试套件
  5. 团队评审
```

#### 措施三：Spec 审计追踪

每条 spec.md 约束记录完整的生命周期：

```markdown
## 📋 审计追踪

| 日期 | 操作 | 操作者 | 理由 | 影响文件数 |
|------|------|--------|------|-----------|
| 2026-04-06 | 创建 | @zhangsan | 架构设计决策 | 0 |
| 2026-04-08 | 强化 | @zhangsan | 循环依赖事故后加强 | 5 |
| 2026-05-12 | 验证 | @lisi | DI 崩溃确认规则有效 | 0 |
| 2026-06-10 | 质疑 | @wangwu | 提出此规则可能过严 | - |
| 2026-06-12 | 修改 | @zhangsan | 明确为"Web 不直接引用 DAL 命名空间" | 12 |
```

**关键字段**：
- `操作者`：谁做的变更
- `理由`：为什么（必须有具体原因，不接受"我觉得"）
- `影响文件数`：这条规则影响了多少文件的修改

#### 措施四：Spec 质疑机制

建立安全、低摩擦的 spec 质疑流程：

```markdown
## 💬 质疑记录

### 质疑 #1（2026-06-10，@wangwu）
**质疑的规则**：§3 第二条 "禁止在 .razor 中写 <style>"
**质疑理由**：
  - MudBlazor 的某些组件需要内联样式才能正确覆盖默认主题
  - 当前规则导致组件样式定制困难
  - 其他 Blazor 项目允许使用 <style> 隔离
**建议方案**：改为 "禁止在 .razor 中写 <style>（除非是 MudBlazor 组件样式覆盖，且限制在 10 行内）"
**决议**：✅ 已采纳（2026-06-12）
**理由**：团队讨论后同意 MudBlazor 样式覆盖的实际需求
```

**质疑流程**：
```
任何人发现 spec 可能有问题
  → 在 spec.md 底部添加质疑记录
  → 团队讨论（异步）
  → 决议：采纳 / 驳回 / 修改
  → 更新 spec.md 和审计追踪
```

**质疑的安全保障**：
- 质疑不需要"证明规则错误"——只需"有合理怀疑"
- 质疑被驳回不丢人——记录"为什么驳回了"对后来者也有价值
- 质疑记录本身就是宝贵的知识

```bash
建议：安排团队审查会议，逐条确认以上规则是否仍然有效。
```

#### 措施六：Spec "日落"机制

对于预防性（`preventive`）和推测性（`speculative`）规则，设定自动过期：

```markdown
### 🚫 [confidence:preventive] [sunset:2026-09-01]
> 此规则在 2026-09-01 前有效，届时需要重新评估或自动降级为"建议"
1. **建议** 所有 Service 方法返回 Result<T> 而非抛异常
```

**日落规则**：
- `validated` 规则：不过期（有事故证据支撑）
- `proven` 规则：12 个月后重新评估
- `consensus` 规则：6 个月后重新评估
- `preventive` 规则：3 个月后重新评估
- `speculative` 规则：1 个月后重新评估或删除

## 三、执行计划

### 阶段划分

```
Phase 0: 研究与设计（本次已完成）
  ├── P0-1: 理解两个问题的本质 ✅
  ├── P0-2: 分析现有 spec.md 体系缺陷 ✅
  └── P0-3: 设计解决方案 ✅

Phase 1: Spec 可信度与审计追踪（基础改造）
  ├── P1-1: 设计 spec.md 增强模板（加入可信度、审计追踪、质疑机制字段）
  ├── P1-2: 改造 spec_md_manager.py（支持新模板、审计记录生成）
  ├── P1-3: 修改 AGENTS.md 中的 spec.md 生命周期规则
  └── P1-4: 在 架构总纲.spec.md 上试点改造（验证可行性）

Phase 2: 自动验证闭环（技术实现）
  ├── P2-1: 设计可验证规则标注格式（[verifiable:xxx] 标注）
  ├── P2-2: 开发 spec 规则解析器（从 spec.md 提取机器可验证规则）
  ├── P2-3: 开发 Roslyn Analyzer（编译时检查）
```
