# 增强版 spec.md 模板设计

> 在原有 6 章节模板基础上，增加可信度分级、审计追踪、质疑记录、Sunset 机制。
> 解决 Problem 2（错误约定误导与修正困难）的核心设计。

---

## 一、设计目标

1. **可信度可见**：每条规则标注可信度等级，避免"猜测"冒充"经验"
2. **变更可追溯**：每次规则变更都有审计记录（谁、什么时候、为什么）
3. **质疑可低摩擦**：任何人都可以安全地质疑 spec 规则
4. **过期可自动**：低可信度规则设自动过期，避免规则腐化

---

## 二、增强模板完整结构

```
1. 文件用途              ← 原有
2. 踩过的坑              ← 原有，增加可信度标注
3. 禁止修改的内容        ← 原有，增加可信度 + 可验证性标注
4. 必须遵守的技术规范    ← 原有，增加可信度标注
5. 允许的操作            ← 原有
6. 当前状态 / 健康检查   ← 原有
7. 维护提示              ← 原有
8. 📋 审计追踪           ← 新增
9. 💬 质疑记录           ← 新增
10. ⏰ Sunset 记录       ← 新增
```

## 三、可信度分级体系

### 3.1 等级定义

| 等级 | 标识 | 星级 | 含义 | 可质疑性 | 默认过期 |
|------|------|------|------|----------|----------|
| 5 | `[confidence:validated]` | ⭐⭐⭐⭐⭐ | 由实际事故验证，有明确证据 | 不可质疑（除非有新证据） | 不过期 |
| 4 | `[confidence:proven]` | ⭐⭐⭐⭐ | 在多项目中验证有效 | 需要充分理由 | 12 个月 |
| 3 | `[confidence:consensus]` | ⭐⭐⭐ | 团队共识，基于经验 | 需要讨论 | 6 个月 |
| 2 | `[confidence:preventive]` | ⭐⭐ | 预防性规则，未实际触发 | 可以质疑 | 3 个月 |
| 1 | `[confidence:speculative]` | ⭐ | 个人偏好或实验性规则 | 鼓励质疑 | 1 个月 |

### 3.2 标注语法

在规则标题后添加 `[confidence:xxx]` 标注：

```markdown
### 🚫 [confidence:validated] 分层架构红线
> **可信度**: ⭐⭐⭐⭐⭐ (由 3 次生产事故验证)
> **验证记录**: 2026-04-08 循环依赖导致编译失败 | 2026-05-12 运行时 DI 崩溃
1. **禁止** Web 项目引用 Infrastructure 项目

### 🚫 [confidence:preventive] 异步方法命名
> **可信度**: ⭐⭐ (预防性规范，未发生过事故)
> **提出者**: @alice | **提出日期**: 2026-06-01
2. **建议** 异步方法使用 Async 后缀

### 🚫 [confidence:speculative] AI 代码风格偏好
> **可信度**: ⭐ (个人偏好，可讨论)
> **提出者**: @bob | **提出日期**: 2026-06-10
3. **建议** 优先使用 LINQ 而非 foreach
```

### 3.3 置信度决策树

```
这条规则是否有生产事故支撑？
├── 是 → [confidence:validated] (⭐⭐⭐⭐⭐)
└── 否 → 是否在多个项目中验证有效？
    ├── 是 → [confidence:proven] (⭐⭐⭐⭐)
    └── 否 → 是否团队共识？
        ├── 是 → [confidence:consensus] (⭐⭐⭐)
        └── 否 → 是否有明确的问题驱动？
            ├── 是 → [confidence:preventive] (⭐⭐)
            └── 否 → [confidence:speculative] (⭐)
```

## 四、审计追踪格式

### 4.1 表格格式

每条规则末尾粘贴审计追踪表格（由工具自动维护）：

```markdown
## 📋 审计追踪

| 日期 | 操作 | 操作者 | 理由 | 影响文件数 |
|------|------|--------|------|-----------|
| 2026-04-06 | 创建 | @zhangsan | 架构设计决策 | 0 |
| 2026-04-08 | 强化 | @zhangsan | 循环依赖事故后加强 | 5 |
| 2026-05-12 | 验证 | @lisi | DI 崩溃确认规则有效 | 0 |
| 2026-06-10 | 质疑 | @wangwu | 提出此规则可能过严 | - |
| 2026-06-12 | 修改 | @zhangsan | 明确为"Web 不直接引用 DAL 命名空间" | 12 |
```

### 4.2 操作类型

| 操作 | 含义 | 适用范围 |
|------|------|---------|
| 创建 | 规则首次写入 | 任何规则 |
| 修改 | 规则内容变更 | 任何规则 |
| 强化 | 规则从"建议"升级为"禁止" | 置信度升级 |
| 放松 | 规则从"禁止"降级为"建议" | 置信度降级 |
| 验证 | 确认规则仍然有效（审查通过） | 任何规则 |
| 质疑 | 有人提出规则可能有问题 | 任何规则 |
| 废除 | 规则被删除 | 任何规则 |

## 五、质疑记录格式

### 5.1 记录格式

质疑记录追加在文件底部：

```markdown
## 💬 质疑记录

### 质疑 #1（2026-06-10，@wangwu）
**质疑的规则**：§3 第二条 "禁止在 .razor 中写 <style>"
**质疑理由**：
  - MudBlazor 的某些组件需要内联样式才能正确覆盖默认主题
  - 当前规则导致组件样式定制困难
  - 其他 Blazor 项目允许使用 <style> 隔离
**建议方案**：改为 "禁止在 .razor 中写 <style>（除非是 MudBlazor 组件样式覆盖，且限制在 10 行内）"
**决议**：✅ 已采纳（2026-06-12）
**理由**：团队讨论后同意 MudBlazor 样式覆盖的实际需求
```

### 5.2 质疑流程

```
任何人发现 spec 可能有问题
  → 在 spec.md 底部添加质疑记录
  → 团队讨论（异步，通过 issue/PR/群聊）
  → 决议：✅ 采纳 / ❌ 驳回 / 🔄 修改
  → 更新 spec.md 和审计追踪
```

### 5.3 质疑安全保障

- 质疑不需要"证明规则错误"——只需"有合理怀疑"
- 质疑被驳回不丢人——记录"为什么驳回了"对后来者也有价值
- 质疑记录本身就是宝贵的知识资产

## 六、Sunset 过期机制

### 6.1 标注语法

```markdown
### 🚫 [confidence:preventive] [sunset:2026-09-01]
> ⏰ 此规则在 2026-09-01 前有效，届时需重新评估或自动降级
1. **建议** 所有 Service 方法返回 Result<T> 而非抛异常
```

### 6.2 默认过期时间

| 置信度 | 默认有效期 | 过期后行为 |
|--------|-----------|-----------|
| `validated` | 不过期 | 保持原样 |
| `proven` | 12 个月 | 降级为 `consensus` 并提醒审查 |
| `consensus` | 6 个月 | 提醒审查 |
| `preventive` | 3 个月 | 提醒审查，可能降级/删除 |
| `speculative` | 1 个月 | 提醒审查，可能降级/删除 |

### 6.3 过期处理流程

```
规则到达 Sunset 日期
  → 工具扫描发现（spec_review_reminder.py）
  → 通知团队审查
  → 决议：
    ├── 保持 → 更新 Sunset 日期 + 更新审计追踪
    ├── 降级 → 修改内容 + 降低置信度
    ├── 升级 → 提高置信度 + 延长 Sunset
    └── 删除 → 从 spec.md 移除 + 记录审计追踪
```

## 八、与可验证规则标注的配合

增强模板与 Problem 1 解决方案（可验证规则标注）**互补而非替代**：

```markdown
### 🚫 [confidence:validated] [verifiable:di] 分层架构红线
<!-- @rule id=WM-ARCH-001 type=dependency-check -->
<!-- @check: Web项目不引用Infrastructure项目 -->
```

两者的关系：
- `[confidence:xxx]` 回答"这条规则有多可信？"（信任问题）
- `[verifiable:xxx]` 回答"这条规则能自动检查吗？"（验证问题）
- `[sunset:YYYY-MM-DD]` 回答"这条规则什么时候过期？"（时效问题）
